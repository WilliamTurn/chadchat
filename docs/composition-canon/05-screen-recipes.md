# Composition Canon 05 — Screen-Type Layout Recipes

Domain: how an individual screen is assembled — the known-good skeleton for each screen archetype, expressed as ordered zones on a continuous surface (per `design-north-star-2026-07-16.md`: Gestalt grouping, editorial hierarchy, no card grids). Compiled 2026-07-23 from cross-source consensus: Material 3 canonical layouts, Apple Human Interface Guidelines (HIG), Nielsen Norman Group (NN/g) page-structure and dashboard research, Baymard Institute (list and detail pages), Refactoring UI (hierarchy-first layout), GOV.UK Design System, plus direct pattern observation of best-in-class fitness and productivity apps via Mobbin (2026-07-23 pull: Hevy, Fitbod, Runna, Ladder, Oura, Apple Fitness, Fitbit, Gymshark Training, Bevel, Nike Training Club).

Every recipe here is a **default with stated conditions, never an absolute**. Deviating is allowed when the content genuinely demands it — but the deviation is a decision to state out loud, not a drift. Each principle is tagged [mechanical] (checkable by rule) or [judgment] (requires a call). Rules derived from app observation rather than a source of record are tagged [judgment] with a "converged-product observation" source note; see the sourcing-honesty notes at the end.

Boundary with the ux-canon: navigation, IA, back behavior, and flow logic are law in `audits/workout-overhaul-2026-07-22/ux-canon/02-navigation-ia-flows.md`; type scale, spacing values, color, and data-viz element rules are law in `.../04-visual-motion-content.md`. This file owns the level between them: which zones a screen has, in what order, with what relative weight.

---

## 1. Recipe grammar — rules that apply to every screen

1. **Assemble every screen as an ordered stack of zones, each answering one user question, in descending priority.** A zone is a region the eye reads as one topic — created by proximity, alignment, and typographic contrast, not by a box. Before layout, write the question list ("What should I do today?" → "How am I trending?" → "What else?"); the screen is that list made visible, top to bottom. — [NN/g inverted-pyramid / page-structure research; Refactoring UI (hierarchy before layout); north star §per-feature checklist] — [judgment]
2. **Every screen has exactly one protagonist zone; name it before styling anything.** One element gets the largest scale and the strongest contrast; everything else supports it. If two zones compete for dominance, the screen has no answer — demote one. — [Refactoring UI; NN/g visual hierarchy] — [judgment]
3. **Separate zones with more space than you use inside them.** The Gestalt proximity rule made mechanical: between-zone spacing must be ≥2× within-zone spacing (the canonical gap table and floor live in comp-canon 06 #8; the ladder itself in 01 #11). When spacing alone can't carry the break, escalate in the canonical rung order: alignment/typography shift, then a section header, then a divider line, then a tint/atmosphere shift — and a box only past all of those, gated by 01 §4. — [Gestalt proximity (NN/g); north star "what replaces cards"; comp-canon 01 #11, 06 #8; ux-canon 04 §2] — [mechanical] *(patched 2026-07-23: mini-ladder reordered to 01 #11; 1.5× floor raised to ≥2×)*
4. **The first phone viewport (~384×~700) contains the screen's answer and its primary action.** What shows before any scrolling is the screen's thesis statement. Chrome (header, tabs, filters) must not eat it: if the user sees only navigation and labels before the fold, the recipe failed. — [NN/g above-the-fold research; Baymard mobile] — [judgment]
5. **Scroll order is priority order.** Everything below the fold must matter less than everything above it. Never park something critical beneath something optional because it was built later — that is appending, not composing. — [NN/g scrolling & attention studies] — [judgment]
6. **Header chrome stays minimal: an orienting title plus at most two actions.** The title answers "where am I" (and matches the label that got the user here — ux-canon 02 #33); actions in the header are only those that operate on the whole screen. Everything else lives in the body or an overflow menu. — [Apple HIG navigation bars; Material 3 top app bar] — [mechanical]
7. **On phones the screen is one column; on desktop it either gains a second pane with a defined role or stays a centered column — it never just stretches.** Material 3's canonical layouts are the consensus menu: feed (one column → wider column), list-detail (list pane + detail pane), and supporting pane (body + secondary pane). Full-width text and full-bleed rows at 1280px are a defect; cap the content measure. — [Material 3 canonical layouts; Apple HIG layout; NN/g line-length research] — [mechanical]
8. **The primary action of any screen lives in the thumb zone on phones — bottom-anchored or within the lower half.** Top-right header buttons are for secondary verbs. (Placement law is ux-canon 02 #27; this file applies it per archetype below.) — [Apple HIG; Material ergonomics; Baymard mobile] — [mechanical]
9. **Do not blend archetypes on one screen.** A screen that tries to be both a browse surface and a live-task surface (or both an overview and a settings panel) fails at both — the density, chrome, and action rules below conflict. If a screen seems to need two recipes, it is two screens. — [NN/g task-focus research; converged-product observation] — [judgment]
10. **State handling is part of the recipe: every archetype below defines where its empty, loading, and error states render.** The default: states render in the zone the content would occupy, at the same position — never as a bare toast, never as a blank region that looks broken. — [NN/g empty states; ux-canon 03 owns state *content*; this file owns their *position*] — [mechanical]

10a. **First-load composition: zones skeleton top-down in priority order, each skeleton mirroring its zone's final rung and rhythm.** The hero zone renders (or skeletons) first, supporting zones after — a screen whose hero pops in last, or whose zone map rearranges as data arrives, fails the recipe even when every loaded zone is right (skeleton-matches-final is 01 #73/ux-canon 04 #110). The pull-to-refresh indicator occupies the gap above the first zone without displacing it; pagination loaders render as one compact row at the list's end, in the list's own column. Skeleton content and timing are ux-canon 03/04's. — [NN/g skeleton research; 01 #73; added 2026-07-23 per completeness sweep THIN #9] — [mechanical]

## 2. Status/overview surface (the "today" screen)

The skeleton, top to bottom: (a) whispered context (date/greeting), (b) **the answer** — today's single recommended action or headline status, (c) today's plan/action zone, (d) supporting metrics in priority order, (e) secondary trends and extras. Oura leads with one large activity number plus a plain-sentence interpretation; Apple Fitness leads with one dominant ring; both then descend into smaller supporting zones.

11. **The top zone answers "what should I do right now?" — not "here is all your data."** An overview surface is answer-first: today's recommended workout / recovery call / next action is the protagonist, readable in under five seconds (north star goal #1). Data exists to justify the answer, below it. — [NN/g dashboard research (answer-first vs data-dump); north star; converged-product observation: Oura, Apple Fitness] — [judgment]
12. **One hero, sized like a headline; every other metric visibly subordinate.** The hero is a single number, ring, or scene at display scale with a spaced-caps label; supporting metrics run at half its visual weight or less. Two heroes = zero heroes. — [Refactoring UI; NN/g dashboards; converged-product observation: Oura's single activity number, Apple Fitness's single ring] — [judgment]
13. **Never lay the overview out as an equal-weight tile grid.** A grid of same-sized metric tiles is the canonical overview defect: it abdicates the ranking decision to the user, exposes the layout grid as the visual language (north star anti-goal), and reads as a settings panel for data. If everything is equally loud, the screen says nothing. — [NN/g dashboard critique; north star explicit anti-goal; negative observation: Fitbit's tile-heavy Today vs Oura/Apple's ranked stack] — [mechanical]
14. **Greeting, date, and branding are whispers, not headlines.** Context line in small type above the hero; it must never be the largest text on the surface. The user knows their own name. — [Refactoring UI (labels are not content); converged-product observation] — [mechanical]
15. **Cap the surface at roughly 3–5 zones, each owning one concept.** Today's action, then two-to-four supporting concepts (e.g. recovery, nutrition, sleep). More than that belongs on section screens reachable in one tap; an overview that scrolls forever is a feed, not an answer. — [NN/g dashboard scope; north star goal #2 (organizational logic in 30s)] — [judgment]
16. **Every zone pairs current state with one obvious way to act on it.** A hydration zone shows the level *and* the log action; a plan zone shows the workout *and* Start. Status with no verb is a poster; verbs live inside the zone they act on, not pooled in a button row. — [focus+context (north star checklist #4); converged-product observation: Hevy/Fitbod start-workout placement] — [judgment]
17. **The overview links out; it does not inline.** History, full stats, and settings are one tap away from their zones, never embedded as scrollable sub-lists inside the today surface. The overview is the top of the hierarchy (ux-canon 02 #12), not a container for the whole app. — [NN/g homepage guidelines; Material 3 feed layout] — [judgment]
18. **When the day's state changes, the surface re-ranks — the recipe is time-aware.** Before a workout, the plan zone dominates; mid-day after completion, the recap and recovery dominate. Reordering *within the overview* by state is expected here and is not the forbidden nav reordering of ux-canon 02 #25. — [converged-product observation: Oura readiness-first mornings, Apple Fitness post-workout recap; Material dynamic content guidance] — [judgment]
19. **On desktop, the hero stays the hero.** Widen to at most two macro columns with the answer zone dominant (top-left, largest); never reflow the ranked stack into equal columns — that recreates the tile grid at desktop width. — [Material 3 feed→pane adaptation; NN/g F-pattern (top-left primacy)] — [mechanical]
20. **First-run overview renders the same skeleton with the setup action as the hero.** Before data exists, the answer zone becomes "set up your first plan / log your first workout" in the hero position; supporting zones show their labeled frames with teach-copy, not blank gaps and not a different screen. — [NN/g empty states; ux-canon 02 #79] — [mechanical]

Characteristic defects: equal-weight tile grid (no answer hierarchy); greeting/date as the largest text; status zones with no verb; the overview inlining whole histories until it becomes an unranked feed.

## 3. List/collection screen

The skeleton, top to bottom: (a) header with title + count/summary, (b) filter/sort controls as a chip row when the list is filterable, (c) the rows, grouped under section headers when a grouping dimension exists (usually date), (d) empty state in the rows' position when there are none. Observed convergence: Runna and Apple Fitness group history under month headers with per-group aggregate stats; Nike Training Club uses thumbnail rows under date headers.

21. **A row is: one primary text, one to three metadata items, one optional trailing affordance — in that visual order.** The primary text is what the user scans by (workout name, exercise name); it gets the strongest weight and left-aligns into one clean column down the screen. Metadata (date, duration, volume) sits smaller, beside or beneath. More than ~3 metadata items per row on a phone turns scanning into reading. — [Material 3 list anatomy; Apple HIG lists; Baymard list-item design; NN/g scannability] — [mechanical]
22. **Pick metadata that differentiates rows, not metadata you happen to have.** In a workout history, duration and volume differentiate; the year, repeated on every row under a "2026" header, does not. Every repeated identical value is noise to delete. — [Baymard list metadata findings; Refactoring UI] — [judgment]
23. **A thumbnail must earn its place: include it only when the image helps recognize or choose the row.** Distinct workout/program photos (Nike Training Club) earn it; a repeated identical dumbbell glyph on every row is decoration that costs a text column. When rows are visually identical in kind, drop the image and spend the width on words and numbers. — [Baymard imagery-in-lists; NN/g image usability; converged-product observation] — [judgment]
24. **Group rows by the dimension users think in — for history, by date — using editorial section headers, not enclosures.** A small spaced-caps header ("MARCH 2026") plus grouped proximity does the work; the group is perceived, not boxed. — [north star grouping; NN/g chunking; converged-product observation: Runna, Apple Fitness, Bevel month grouping] — [mechanical]
25. **Put the group's aggregate in its header line — caps for the label only, sentence case for the aggregate.** The spaced-caps treatment covers ONLY the 1–3-word group label ("MARCH 2026"); the aggregate ("6 workouts · 4h 12m") renders beside it in sentence-case `--mute` — multi-word aggregates in caps are exactly the defect Q-DS-4 was written against ("extremely bad", owner 2026-07-17). Built right, the header line turns a divider into information and gives the list a stats layer for free; converged across Runna and Apple Fitness. — [converged-product observation; NN/g information scent; Q-DS-4] — [judgment] *(patched 2026-07-23: example re-split to keep caps at 1–3 words per Q-DS-4)*
26. **Whitespace first, hairlines second, boxes never (default).** Separate rows with spacing alone while rows are single-line and rhythm is regular; add inset hairline dividers only when rows are dense or multi-line and spacing alone stops working. Per-row containers are the escape hatch of last resort (north star). — [north star; Material 3 divider guidance ("use sparingly"); Apple HIG inset separators] — [judgment]
27. **The whole row is the tap target; one row, one destination.** No competing tap zones inside a row except an explicit trailing control (e.g. a start button), which must be visually distinct and ≥ the platform target size. — [Apple HIG; Material 3 list interaction; ux-canon 01 owns target sizes] — [mechanical]
28. **Filters and sort live between header and rows, visible, as a horizontally scrollable chip row when present — and active filters stay visible.** (Filter *state* rules are ux-canon 02 #39/#70; position is fixed here.) Pin the chip row when the list is long enough that users filter mid-scroll. — [Baymard faceted navigation; Material 3 chips; converged-product observation: Apple Fitness sessions filter chips] — [mechanical]
29. **Keep row height rhythm constant within a group.** Uniform vertical rhythm is what makes a cardless list read as a list; one double-height row mid-list breaks the scan column. Variation is allowed *between* groups or for a deliberate featured row at top. — [Refactoring UI rhythm; NN/g scannability] — [mechanical]
30. **The empty state renders exactly where the rows would be: named section, why it's empty, one action.** Centered in the content zone, not a toast, not a bare "0 results". (Content rules: ux-canon 02 #40, 03.) — [NN/g empty states; Material 3] — [mechanical]
31. **A gallery (grid) layout is the list variant for when the image IS the content.** Program covers, physique photos, meal photos: 2 columns at phone width, text reduced to a caption. If users choose by reading rather than by looking, it's a list, not a gallery. — [Baymard grid-vs-list findings; Apple HIG collections] — [judgment]
32. **On desktop, a frequently-drilled list becomes list-detail (list pane left, detail pane right); a terminal list stays a centered column.** List-detail is the Material 3 canonical layout for history-type content and the Linear/Things convergence; use it when users open many rows per visit. Never present a full-width stretched phone list at 1280px. — [Material 3 list-detail canonical layout; converged-product observation: Linear, Things, Gmail-class apps] — [mechanical]

32a. **The search variant of the list recipe: the search field sits between the header and the filter row (or replaces the filter row while active); an executed query echoes above the rows with its result count ("12 results for 'bench'"); recent searches and suggestions render in the rows' position while the field is focused and empty.** No-results is its own state, distinct from never-had-anything (#30): it names the query, offers clear-search, and — when filters are active — a clear-filters path, because "no results" with hidden filters on reads as a broken feature. Search behavior (debounce, matching, history) is ux-canon 02 §6; the geometry is fixed here. — [Baymard search results, NN/g site search; added 2026-07-23 per completeness sweep THIN #1] — [mechanical]

32b. **In selection mode, a cardless list shows per-row selection with a leading control column and whole-row toggle taps — rows never grow boxes to look selectable.** The leading checkmark control shifts every row's content right by one fixed allowance (all rows together, selected or not), and the selected row's state renders as a full-bleed tint highlight (rung 5), not a border. The chrome transformation (top bar, bulk action bar) is 08 #59; bulk-action behavior is ux-canon 08 §B8. — [M3 selection patterns, HIG edit mode; 08 #59; added 2026-07-23 per completeness sweep THIN #2] — [mechanical]

Characteristic defects: repeated identical thumbnails; metadata soup (4+ facts per row, none differentiating); per-row boxes recreating a card feed; empty state as a blank area or toast; desktop rendering as a stretched phone list.

## 4. Detail screen (a workout, an exercise)

The skeleton, top to bottom: (a) identity zone — media if media identifies the thing, then title with subordinate classification metadata, (b) key-facts band — the 2–4 numbers that summarize it, (c) primary action, (d) body sections in descending relevance (instructions, history, records, related). Observed convergence: Fitbod's exercise page (video → "Dip" → "Triceps, Chest, Shoulders" → instructions), Hevy's (animation → title → muscles → records/history), Tonal's (video → title → muscle diagram → instructions).

33. **The identity zone answers "what is this?" in one fixation: title dominant, classification metadata one step down.** Title at display scale; muscles/category/equipment as a smaller secondary line directly beneath (proximity binds them). If the metadata line visually rivals the title, the hierarchy is broken. — [Refactoring UI title/meta hierarchy; converged-product observation: Fitbod, Hevy] — [mechanical]
34. **Lead with media only when the media identifies or teaches the thing — then let it own the top, with the title immediately on or under it.** An exercise demo earns full-bleed top placement (every observed exercise page does this); a workout-session detail has no identifying image, so it leads with title + facts instead. Never a decorative stock hero. — [Apple HIG imagery; Baymard product-page media; converged-product observation: Tonal, Fitbod, Ladder] — [judgment]
35. **Follow identity with a key-facts band: the 2–4 numbers that summarize the thing, as figures with spaced-caps labels, scannable in one row.** Sets/volume/duration/PR — numbers first, editorial labels under them, no boxes. This band is the detail screen's "answer" (grammar rule #4). — [Baymard key-specs-before-prose finding; north star editorial numerals; converged-product observation] — [mechanical]
36. **The primary action is visible without scrolling and repeated or pinned when the body is long.** "Start workout" / "Add to workout" sits directly under the facts band on phones (thumb-zone pinned when the page scrolls far). A detail page whose only verb is below three screens of prose is a brochure. — [Baymard above-the-fold CTA; Apple HIG; converged-product observation: Tonal's pinned Add Movement] — [mechanical]
37. **Body sections descend in relevance, each under an editorial header: how-to/instructions, then history/records, then related items last.** Order by what the user came for (per-content call), and keep every section skimmable — the header plus first line must say whether to stop. — [NN/g page chunking; converged-product observation: Fitbod, Hevy section orders] — [judgment]
38. **Use in-page tabs on a detail screen only when body sections are long AND independently visited; otherwise one continuous scroll.** Hevy tabs Summary/History/How-to because each is a destination; short sections tabbed apart just hide content. In-page tabs must not look like app navigation (ux-canon 02 #24). — [Apple HIG segmented controls; NN/g tabs-vs-scroll; converged-product observation] — [judgment]
39. **In a history/records section, chart precedes table and latest precedes oldest.** One trend chart (or headline record) first, raw entries after — the Fitbod pattern (record number + one chart, then "Exercise History" entries). Chart element rules are ux-canon 04 §8. — [converged-product observation: Fitbod, Hevy; NN/g data-first summaries] — [judgment]
40. **On desktop, identity+media and key facts sit side by side above a single-column body.** The two-pane top (media left, title/facts/action right) is the Airbnb/Baymard-consensus detail adaptation; the prose body stays one readable column, not stretched. — [Baymard product-page layout; Material 3 supporting-pane; converged-product observation: Airbnb-class detail pages] — [mechanical]

Characteristic defects: title and metadata at equal weight (no identity); primary action buried below prose; every body section given equal length and weight; a decorative hero image that identifies nothing; tabs hiding two paragraphs each.

## 5. Live-task/logging screen (mid-workout)

The skeleton: (a) thin pinned status strip — elapsed time/progress plus the single exit, (b) the current item, visually dominant, with its inputs, (c) next-up preview, subdued, (d) dominant next action pinned in the bottom thumb zone. Observed convergence: Runna (big timer top, active set boxed-and-accented, Pause + Next Exercise pinned bottom), Ladder (progress top, huge rest countdown center, next-up chip), Hevy (timer + Finish in top bar, active set row highlighted, previous-session values prefilled), Fitbod (rest timer as bottom sheet over the set list).

41. **A live screen answers exactly three questions at a glance: where am I in the session, what am I doing now, what happens next.** Elapsed/progress (small, pinned top), current exercise/set (dominant center), next action (pinned bottom). Anything that doesn't serve one of those three questions comes off the screen. — [NN/g task-focus; Apple HIG focused states; converged-product observation: Runna, Ladder, Hevy — unanimous] — [judgment]
42. **Session status is a thin pinned strip, not a zone: elapsed time or progress at reading size, top of screen, always visible.** It must survive scrolling — mid-workout the user checks it at arm's length between sets. — [converged-product observation: unanimous across Hevy, Runna, Ladder; Material 3 progress guidance] — [mechanical]
43. **The current item dominates; completed items dim; upcoming items whisper.** Three visibly distinct states — active (scale/accent/contrast), done (checked and receded), pending (present but subdued) — so "where am I" is answerable with the screen at arm's length. Equal weight for done and current sets is the classic defect here. — [figure-ground (north star); converged-product observation: Runna's Active set, Hevy's highlighted row] — [mechanical]
44. **One dominant next action, full-width in the bottom thumb zone, that always names the next thing: Log set → Rest → Next exercise → Finish.** The button is the session's engine; it never moves, and its label tracks the state machine. Secondary controls (pause, skip) sit smaller beside or above it. — [Apple HIG; Material bottom-action guidance; converged-product observation: Runna Pause/Next, Ladder] — [mechanical]
45. **Chrome disappears during a live task: no tab bar, one explicit exit (Finish / discard) in the status strip.** This is the sanctioned focused-mode exception to persistent tabs (ux-canon 02 #14); the exit must remain visible so it never becomes a trap (02 #30). — [Apple HIG modality/focused modes; Material full-screen guidance; converged-product observation: unanimous] — [mechanical]
46. **Density flips from browse to glance: numbers a scale step larger, targets larger, fewer items per viewport than any browse screen.** The screen is read at distance, sweaty, one-handed, between sets. If the live screen and the history screen have the same type density, the live screen is wrong. — [Apple HIG glanceability (Watch/live contexts); converged-product observation: Ladder's poster-scale timer] — [judgment]
47. **Inputs are prefilled from last time and adjusted, not typed from scratch.** Show previous-session values in place (Hevy's "PREVIOUS" column), default the input to it, adjust by steppers/numeric pad. Logging a set should be one confirm, not three fields. — [converged-product observation: Hevy, Fitbod prefill; NN/g input-effort minimization] — [judgment]
48. **The rest timer is an overlay (sheet or in-place takeover) on the session — never a navigation away.** Countdown at poster scale with ±time adjust and Skip; the session context stays visible or one gesture away beneath it. — [converged-product observation: Fitbod bottom sheet, Ladder takeover, Hevy Live-Activity pattern — unanimous on no-navigation] — [mechanical]
49. **Everything actionable sits in the lower half of the phone screen.** Upper half is display (status, current item); lower half is hands (inputs, actions). One-handed operation is the design condition, not an accessibility nicety. — [Apple HIG reachability; Baymard thumb-zone; converged-product observation] — [mechanical]
50. **Re-entry restores the live screen exactly: lock, app-switch, or accidental back lands the user on the current state instantly, no reconstruction.** (State persistence mechanics belong to other canons; the recipe requirement is that the screen has one canonical "current state" render it can always return to — the Hevy Live Activity pattern extends it to the lock screen.) — [ux-canon 02 #44/#48; converged-product observation] — [mechanical]
51. **On desktop/tablet, the live layout stays a single focused column at phone-like width — it does not gain panes.** A live task never benefits from more simultaneous information; center the column, enlarge the type, leave the margins empty. — [Material canonical layouts (feed, narrow); Apple HIG focused modes] — [judgment]

Characteristic defects: browse-screen density during a live task; the primary action floating mid-content instead of pinned; done/current/upcoming sets at equal visual weight; rest timer as a separate screen that orphans the session; tab bar still visible mid-workout.

## 6. Form/settings screen

The skeleton: (a) title, (b) grouped rows under small editorial section headers, ordered by frequency of use, (c) destructive zone — isolated, last, (d) fine print (version, legal) at the very bottom. The consensus model is the iOS Settings grammar rendered cardlessly: grouped label-left/control-right rows.

52. **Group settings into labeled topic sections (Account, Training, Notifications…), groups bound by proximity under spaced-caps headers — not boxed panels.** Grouping is the entire usability of a settings screen; a flat 20-row list is a junk drawer. — [Apple HIG settings; Material 3 lists; GOV.UK question grouping; north star] — [mechanical]
53. **A settings row is label left, current value or control right.** Toggle for on/off, current-value text + disclosure for anything with its own sub-screen, so users can read the state of everything without entering anything. — [Apple HIG; Material 3 list anatomy] — [mechanical]
54. **Order sections and rows by frequency of use, not alphabet or org chart.** What users change weekly (units, notifications, plan) at top; what they touch once (legal, data export) at bottom. — [NN/g menu-ordering; ux-canon 02 #10] — [judgment]
55. **Forms and settings are one column at every width; on desktop, a readable column left-anchored to the page grid per forms canon 03 #38 (centered only in centered compositions), never side-by-side fields.** Multi-column forms cause skipped fields and broken completion order — one of Baymard's most replicated findings. Desktop settings may add a section-nav rail (Material supporting pane), but the fields themselves stay one column. — [Baymard single-column forms; GOV.UK; Material 3; forms canon 03 #38] — [mechanical] *(patched 2026-07-23: "centered" deferred to 03 #38's left-anchor rule)*
56. **Instant-apply and batch-save never mix on one screen.** Toggles that apply immediately, or a form with one sticky Save — pick per screen. A screen where some rows commit instantly and others await a Save button makes every change feel uncertain. — [Apple HIG (instant-apply settings); GOV.UK form patterns; NN/g] — [mechanical]
57. **Destructive actions (log out, delete account, reset data) live alone in the final zone, visually distinct, never adjacent to a safe action.** Isolation by position (last), by color (destructive style per ds.css), and by spacing — a fat-finger between "Save" and "Delete account" must be geometrically impossible. Confirmation mechanics are the interaction canon's; the *placement* is fixed here. — [Apple HIG destructive styling; Material dialogs/actions; NN/g error prevention] — [mechanical]
58. **Long settings surfaces get either a hub-and-spoke split (rows → sub-screens) or search — never one endless scroll.** Past roughly two screens of rows, split by section; past several sub-screens, add settings search (the iOS/Android convergence). — [Apple HIG settings search; Android settings guidance] — [judgment]
59. **Version, build, and legal links render as fine print at the absolute bottom.** They must exist (support needs them) and must be the least prominent text on the screen. — [platform convention, universal] — [mechanical]
60. **Field-level anatomy (labels above inputs, validation timing, input types) follows the forms rules in ux-canon 01/02 §8** — this recipe only fixes the screen skeleton around them. — [cross-reference] — [mechanical]

Characteristic defects: destructive action adjacent to primary; alphabetical or team-structured grouping; mixed instant/batched commit on one screen; two-column desktop forms; missing current-value text on disclosure rows (forcing users to enter every sub-screen to learn state).

## 7. Stats/progress screen

The skeleton: (a) time-range control, once, at top, governing the whole surface, (b) hero insight — one headline number/record with its trend and a plain-sentence interpretation, (c) supporting metric zones in goal-relevance order, each an assembled chart+context unit, (d) links out to per-metric detail. Observed convergence: Fitbod leads a progress page with the projected-1RM record number and one chart, then lists records as number rows; Oura pairs its number with a sentence ("You reached 40% of your activity goal").

61. **Lead with one hero insight, not a wall of charts.** The top zone is the single most goal-relevant fact — current strength trend, this-week volume vs plan, latest PR — at display scale with its trend. Charts support the story; they are not the story. A grid of equal charts is the stats-screen version of the tile-grid defect (#13). — [NN/g dashboard research (one key message); Refactoring UI; converged-product observation: Fitbod, Oura] — [judgment]
62. **Every chart ships as an assembled unit: question-title, headline number, the chart, and a comparison anchor — bound by proximity into one zone.** "Bench press — 100 lb (+5 vs May)" above the trend line. A chart floating without its number and its "compared to what" is decoration. (Element-level chart rules — axes, marks, color — are ux-canon 04 §8.) — [NN/g chart-context research; dataviz consensus; converged-product observation] — [mechanical]
63. **Numbers first, charts second, tables last.** Most progress questions ("did I improve?") are answered by a figure with a delta; render the number row, add the sparkline/trend when shape matters, and reserve full tables for the drill-in screen. Fitbod's records section is number rows with one chart — not five charts. — [NN/g data-display hierarchy; converged-product observation: Fitbod] — [judgment]
64. **One time-range control at the top governs the whole surface.** Per-chart range pickers desynchronize the story ("this week" hero over a "last year" chart) and double the chrome. Range choice is screen state (URL-reflected, ux-canon 02 #53). — [NN/g dashboard filters; converged-product observation: Bevel "Last 30 days" as page subtitle] — [mechanical]
65. **Interpret in plain sentences.** Each major zone carries one line of prose stating what the data means ("Volume is up 12% over four weeks"). Editorial interpretation is the difference between a report and a coach — and it is where this product's voice can live legitimately. — [NN/g dashboards ("so what?" test); converged-product observation: Oura] — [judgment]
66. **Order metric zones by relevance to the user's stated goal, not by data availability.** A strength-goal user sees strength trends before step counts. If the product knows the goal, the recipe must use it. — [NN/g user-goal ordering; north star checklist #1] — [judgment]
67. **The stats surface is an overview that links out: each zone drills into a per-metric detail screen (recipe §4) for full history.** Cramming every exercise's full history onto one surface produces the chart wall; progressive disclosure is the mechanism. — [NN/g progressive disclosure; Material list-detail] — [mechanical]
68. **Insufficient data renders the zone's frame with a stated threshold, not a hidden zone and not an empty chart.** "No data yet — log 3 sessions to see your trend" in the zone's position (Hevy's "No data yet" panel). Zones silently missing make users think the feature is broken. — [NN/g empty states; converged-product observation: Hevy] — [mechanical]
69. **On desktop, supporting zones may sit two-across; the hero never shares its row.** Preserve ranked reading order left-to-right, top-to-bottom; identical chart sizes across all zones recreate the wall. — [NN/g F-pattern; Material canonical layouts] — [mechanical]

Characteristic defects: wall of equal-sized charts with no hero; charts without comparison anchors ("8,412 — is that good?"); per-chart time-range pickers; hiding zones with insufficient data; goal-irrelevant metrics ranked first because the data was easy.

## 8. Chat surface (AI coach)

The skeleton: (a) minimal header — who you're talking to plus at most one action, (b) the message stream, bottom-anchored, (c) suggestion chips when replies are offered, directly above (d) the composer, pinned to the bottom, keyboard-aware. Conversational *behavior* (streaming, tool use, error recovery) is ux-canon 07's; this recipe fixes the geometry.

70. **The stream owns the screen: header and composer are thin bands, and everything between them is messages.** Any persistent element that isn't the stream or the composer must justify itself against lost conversation height — on a ~384px phone, a fat header costs two messages. — [NN/g chat-UI research; Apple HIG messaging convergence] — [judgment]
71. **The stream is bottom-anchored: newest at the bottom, screen opens scrolled to the latest exchange, history above.** Auto-scroll follows new messages only while the user is already at the bottom; a "jump to latest" affordance appears once they've scrolled up. — [universal messaging convention (Jakob's Law); NN/g chatbot usability] — [mechanical]
72. **User messages sit right-aligned in contained bubbles; the coach's replies read as left-aligned editorial text, full-measure, uncontained.** This is the converged AI-assistant layout (ChatGPT/Claude-class, 2024–2026): the assistant's longer, structured prose needs a reading measure, not a balloon; the user's short turns keep the bubble that says "you said this." The user bubble is an EARNED container — it passes 01 #41's provenance test (content not in the app's voice gets a marked boundary), which is why this recipe may prescribe it without violating the cardless default. It also happens to be the cardless answer. — [converged-product observation: AI-assistant apps 2024–2026; NN/g AI-chat studies; 01 #41] — [judgment] *(patched 2026-07-23: earning test cited per sweep item 8)*
73. **Message text never exceeds a readable measure: ~75–80% of width on phones, capped at prose measure (~65–75ch) on desktop, centered column.** Full-width text at desktop width is unreadable; a desktop chat is a centered column with air, not a stretched phone. — [NN/g line length; ux-canon 04 §1; converged-product observation] — [mechanical]
74. **Timestamps and day markers are whispers, grouped — a small centered marker when the conversation crosses a time gap — never a stamp on every message.** Consecutive messages from the same speaker within minutes also group (tightened spacing, one attribution). — [messaging convergence; Gestalt proximity for turn-grouping] — [mechanical]
75. **The composer pins to the bottom: rounded field + send, growing with content up to ~5 lines then scrolling internally; the keyboard pushes the whole surface up, never covers the last message.** Safe-area padding included; send activates only when there's content. — [Apple HIG text entry; Material text-field guidance; universal messaging convergence] — [mechanical]
76. **Suggested replies render as a single row of chips directly above the composer — where the answer will be typed — and vanish once the user acts.** (When to offer them is ux-canon 07's call.) — [Material chips; converged-product observation: AI-assistant apps] — [mechanical]
77. **The coach's structured content (a plan, a table, numbers) renders as formatted editorial blocks inside the reply flow — never screenshots-of-UI or nested boxes-in-bubbles.** The uncontained assistant column (#72) exists precisely so real typography and data layout can happen inside a reply. — [converged-product observation: AI-assistant apps; north star] — [judgment]
78. **A brand-new chat renders the composer plus a short capability introduction and 2–4 starter prompts in the stream's position — not an empty void.** First-run content rules live with ux-canon 07; position is fixed here: the intro sits where messages will appear, so the geometry never shifts. — [NN/g chatbot onboarding; converged-product observation] — [mechanical]

Characteristic defects: bubbles on both sides suffocating the coach's longer replies; a header stealing stream height; the keyboard covering the latest message; timestamps stamped on every message; desktop chat as a full-width stretched phone.

## 9. Onboarding / empty first-run (and any stepped flow — see #85a)

The skeleton per step: (a) whisper-weight progress indicator, (b) the question or idea as the headline — the screen's only headline, (c) the input or options, large-target, (d) Continue pinned in the bottom thumb zone with Skip beside/above it. Flow logic (step count, skippability, value-first ordering) is ux-canon 02 §7; this recipe fixes each screen's skeleton.

79. **One idea per screen: a single question, a single concept, a single decision.** The headline IS the question ("What's your goal?"), set at display scale in the top third; supporting copy is one short line beneath it. Two questions on one onboarding screen is two screens welded together. — [GOV.UK one-thing-per-page; NN/g wizards; ux-canon 02 #84] — [mechanical]
80. **Options are large tap targets filling the middle zone — full-width rows or a 2-up grid, comfortably thumbable, selection state unmistakable.** Onboarding is where users judge the product's quality in seconds; cramped radio buttons at the first question set the tone. Option tiles are earned containers: each is one whole-tile tap target, passing 01 #39's single-target test — which is why the recipe may draw their edges. — [Apple HIG onboarding; Material selection patterns; converged-product observation: Runna/Ladder-class onboarding; 01 #39] — [mechanical] *(patched 2026-07-23: earning test cited per sweep item 8)*
81. **Continue lives in the same pinned bottom position on every step, with Skip visible near it.** Spatial memory turns a 6-step flow into a rhythm; a Continue that wanders (bottom, then top-right, then inline) makes each step a search. — [NN/g consistency; GOV.UK; converged-product observation — near-unanimous pinned bottom CTA] — [mechanical]
82. **Progress is a whisper at the top — thin bar or "2 of 5" — present but never competing with the headline.** (Whether to show it at all: ux-canon 02 #85.) — [NN/g wizards; Material progress] — [mechanical]
83. **Value/preview screens alternate with ask screens and use the same skeleton, with the idea (an illustration or a preview of the user's forming plan) in the middle zone.** Showing the plan assembling from their answers is the strongest payoff pattern (ux-canon 02 #77's "visible payoff" rendered literally). — [growth.design case studies; converged-product observation] — [judgment]
84. **A first-run empty state is the archetype screen's own recipe with teach-content in the content zones — never a different, generic screen.** Empty history = the list recipe with the empty state in the rows' position (#30); empty overview = the overview recipe with setup as hero (#20). The user learns each screen's shape from its very first render. — [NN/g empty states; Material] — [mechanical]
85. **Decoration never displaces the decision: any illustration shares the screen with the question and options, capped so options and Continue stay above the fold at ~384px.** A full-viewport mood image with the question below the fold is a poster, not a step. — [grammar rule #4; NN/g above-the-fold] — [mechanical]

85a. **This section's step skeleton applies to ANY stepped flow — plan builder, guided setup, multi-step edits — not only onboarding.** Outside onboarding, the progress element may be a compact horizontal stepper (numbered dots or segments) in the same whisper position at the top, never competing with the headline; the trigger for splitting a form into steps is forms canon 03 #41, and step mechanics (validation-per-step, back behavior) remain ux-canon 01/02's. A stepped flow that invents its own skeleton per step is the defect this section exists to prevent. — [NN/g wizards, GOV.UK; forms canon 03 #41; added 2026-07-23 per completeness sweep THIN #6] — [mechanical]

Characteristic defects: multiple questions per screen; Continue moving between steps; a decorative hero pushing options below the fold; a generic "welcome" empty screen replacing the archetype's own skeleton on day one.

## 10. Celebration / completion screen *(recipe added 2026-07-23: completeness sweep MISSING #3)*

The skeleton, top to bottom: (a) the direct Home link in the top position (decided, Q-28), (b) the verdict — one headline statement of what was accomplished, (c) the result numerals — the session's 2–4 key stats, (d) earned recognition (records, streaks) only when actually earned, (e) "Back to Workouts" at the bottom (decided, Q-28). This is the airy density pole 02 invokes (02 #2, #21, #24, #38) — composed air, not leftover space.

86. **A completion screen is a verdict, not a report: one headline statement of the accomplishment, at display scale, is the protagonist.** "Workout complete" plus the single most meaningful fact of the session — not a dashboard of everything logged. It is a one-time emotional moment (02 #2), so it earns generous, composed air; a centered composition is legitimate here (02 #44, 08 #49). — [HIG (celebratory moments), NN/g task-completion; 02 #2/#44; converged-product observation: Apple Fitness, Oura recap moments] — [judgment]

87. **Result numerals come second, as one key-facts band: the 2–4 stats that summarize the session (duration, volume, sets), figures with spaced-caps labels — never a data-dump.** Same geometry as the detail screen's facts band (#35). The full per-set breakdown lives on the session's detail screen (recipe §4), one tap away — the celebration links to it, it does not inline it. — [#35's geometry; Tufte (summary before detail); converged-product observation] — [mechanical]

88. **Records and streaks render in the earned-reward treatment only when actually earned; absent achievement = absent zone.** Gold (`--reward`) is earned, never promised (owner ruling 2026-07-19) — so no empty "no records this time" slot, no grayed-out trophy, no target dressed as a reward. When a record IS hit, it may outrank the stats band (the moment's real headline). **One owner-sanctioned exception (2026-07-23, decision log): the workout-completion medal is gold on every finish — completing a workout counts as earning it. This exception covers the completion medal only; everything else on the celebration and everywhere else in the app follows the earned-only rule.** — [ds.css `--reward` contract, ux-canon 08 (celebration ethics); north star; owner decisions 2026-07-19 + 2026-07-23] — [mechanical]

89. **Navigation is exactly the two decided exits plus at most one forward action: the Home link at top, "Back to Workouts" at bottom (both decided — Q-28), and optionally one contextual next step.** No chores between the user and the exit: no rate-us, no share-nag, no upsell interposed on the completion moment. — [Q-28 (owner-decided links); NN/g (post-task flows); ux-canon 08 engagement ethics] — [mechanical]

90. **A celebration collects nothing: inputs (notes, RPE, duration edits) happen on the finish step BEFORE this screen — never on it.** A confirm is a decision surface and a celebration is a reward surface; fields on either are the same category error (comp-canon 04 §12). If the product wants post-workout notes, that is the finish step's job. — [comp-canon 04 §12; NN/g; converged-product observation] — [mechanical]

91. **A share affordance, when built, is a quiet secondary near the result numerals — one control, never a modal interruption and never the protagonist.** Sharing serves the user's pride, not the product's growth loop; it must be skippable by simply not tapping it. — [ux-canon 08 (sharing), HIG; converged-product observation: Strava/Apple Fitness share placement] — [judgment]

92. **This recipe is the house milestone-moment skeleton: PR celebrations, streak milestones, and future milestone screens (Q-F proposals) reuse it — swapping the verdict and numerals, keeping the structure.** One celebration grammar app-wide; a milestone that invents its own layout breaks the sibling rule (grammar rule #9's spirit, 01 #71). — [Q-F (milestone process); 01 #71] — [judgment]

Characteristic defects: a data-dump replacing the verdict; form fields on the celebration; an empty "no records" slot; upsell or rating prompts blocking the exit; gold used for an unearned target.

## 11. Paywall / plan selection / locked state *(recipe added 2026-07-23: completeness sweep MISSING #4)*

The skeleton of the upgrade surface, top to bottom: (a) value statement as the headline, (b) tier options as selectable tiles, (c) the selected tier's feature list, (d) one primary CTA for the selected tier, (e) restore-purchase and legal fine print at the absolute bottom. Locked in-place states follow #93. Purchase-flow law (pricing honesty, cancel paths, no dark patterns) is ux-canon 02 §12; this recipe owns only the screen's composition.

93. **A locked feature renders in place, recognizably itself, under the approved frost treatment — never a blank slot, never a bare padlock row.** The Home locked state (approved) is the house instance: the zone keeps its real structure and position, frosted, with one unlock affordance — so the user learns what exists and where it will live. A locked zone that vanishes teaches users the feature doesn't exist; one replaced by generic upsell chrome breaks the screen's recipe. — [approved Home locked state; NN/g (visibility of features); Baymard (gated content)] — [judgment]

94. **Plan-option tiles are the canonical selectable-container case: each tier passes 01 #39 (the whole tile is the select target) and all tiers get identical containment; selection state is unmistakable.** A recommended tier may be pre-selected and marked — but emphasis uses hierarchy (scale, color, one badge), never a different containment species for one tile (01 #69). — [01 #39/#69; Baymard (plan selection); M3 selection] — [mechanical]

95. **One primary CTA serving the currently selected tier — never one loud CTA per tier competing down the page.** The CTA names the commitment plainly ("Start Pro — $X/month") and sits below the tiers in the thumb zone (08 #8), pinned when the feature list scrolls. Selecting a different tier updates the one CTA; it does not spawn another. — [Baymard checkout research; 08 #8/#9; ux-canon 02 §12] — [mechanical]

96. **Tier comparison at 320–384px runs as stacked tier tiles with per-tier feature summaries (or one feature list with per-tier marks) — never a horizontally scrolling comparison table.** Comparison-critical facts must be simultaneously visible or one tap away (02 #12's eye-span rule); a sideways-scrolling matrix at phone width hides exactly what the user is trying to compare. Desktop may render the side-by-side comparison the phone stacks. — [Baymard (mobile plan comparison), 02 #12, 07 #19] — [mechanical]

97. **Price, billing period, and trial terms render inside the tier tile, at decision point — and the qualifying fine print ("cancel anytime", renewal terms) sits directly adjacent to the CTA (08 #38), with restore-purchase and legal links as fine print at the absolute bottom (#59's slot).** Cost discovered after the tap is a trust defect, not a density win; nothing price-relevant hides behind disclosure (02 #52 — required information is exempt from the density valve). — [Baymard (price transparency), 08 #38, 02 #52; ux-canon 02 §12] — [mechanical]

98. **The upgrade surface keeps the house voice and recipe grammar: neutral product copy (no Chad-voice pressure), one protagonist (the value statement), zones separated by the canonical ladder — a paywall is still a screen of this app, not a foreign template.** Chad's harsh voice lives only in chat (house copy rule); countdown timers, fake scarcity, and guilt copy are banned by ux-canon 02 §12's anti-dark-pattern law. — [house copy rules, ux-canon 02 §12; grammar rules #1–2] — [judgment]

Characteristic defects: locked zones that vanish instead of frosting; a CTA per tier; sideways-scrolling comparison tables at phone width; price revealed only after the tap; dark-pattern urgency copy.

## Contested / no-consensus

- **Chevrons/disclosure indicators on list rows**: Apple HIG ships them on every drill-in row; Material 3 omits them by default and treats the whole-row ripple as affordance enough. Fitness apps split (Bevel arrows, Runna none). Pick one per this product and enforce it. [contested]
- **Dividers vs pure whitespace in dense lists**: Material historically leaned dividers, Apple uses inset hairlines, modern editorial/web design (and the north star) leans whitespace-only. Consensus exists only at the extremes (sparse lists need nothing; dense multi-line lists need something). The crossover point is a judgment call. [contested]
- **AI chat: symmetric bubbles vs editorial assistant column**: messaging apps (iMessage/WhatsApp) are symmetric-bubble; AI assistants converged on uncontained assistant text. #72 takes the AI-assistant side for a coach product, but the messaging tradition is genuinely alive and some coach apps ship bubbles. [contested]
- **FAB vs pinned full-width bottom button for a list's primary action**: Material 3 still ships the FAB; Apple-platform and most observed fitness apps use pinned full-width buttons or header "+". FABs also sit awkwardly in a cardless editorial surface. Recipe default here is pinned/inline, but this is a platform-culture split, not consensus. [contested]
- **User-customizable overview layouts** (Apple Fitness/Fitbit "Edit" mode for reordering summary zones) vs a fixed, opinionated ranking: personalization respects user control; a coach product arguably must keep the answer-first ranking authoritative. No cross-source consensus; #18's state-driven re-ranking is the middle path taken here. [contested]
- **Detail screens: long scroll vs in-page tabs**: Hevy tabs, Fitbod scrolls, Tonal scrolls with a toggle for media only. #38's "tab only long, independent sections" is the majority reading of NN/g, not a settled law. [contested]
- **Desktop list-detail split vs separate detail pages** for history-type content: Material 3 canonicalizes the split pane; much of the responsive web keeps separate routed pages (simpler URLs, simpler state — ux-canon 02 §5 interactions). Both are defensible for this product. [contested]
- **How much of the first viewport the live-task hero may consume**: Ladder devotes nearly the whole viewport to the timer/video; Hevy keeps a dense multi-set table visible. Both are top-tier and deliberate (coached classes vs self-directed lifters). The three-questions rule (#41) is consensus; the hero's exact scale is product positioning. [contested]
