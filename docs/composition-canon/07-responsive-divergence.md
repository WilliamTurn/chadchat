# Composition Canon 07 — Responsive Divergence

Domain: what changes between a ~384px phone and desktop, what must NOT change, and how a composition reflows. This file owns layout REFLOW — the grammar of how one screen becomes correct at every width from 320px to desktop. Mobile BEHAVIOR (touch targets, thumb zones, keyboards, performance) is law in ux-canon 06 (`audits/workout-overhaul-2026-07-22/ux-canon/06-performance-mobile-trust.md`) and baseline layout tokens live in ux-canon 04 §2; those are referenced, not restated. Part of an eight-file composition canon.

House context this file assumes: the north star (`design-north-star-2026-07-16.md`) applies at ALL widths — cardless composition is not a mobile-only rule; the owner's phone is ~384px; the house smoke test renders every surface at six widths (320–1280); the 12px type floor is permanent.

Tags: [mechanical] = objectively checkable/automatable; [judgment] = requires human evaluation. [contested] items are quarantined at the bottom.

## A. The invariants — what a width change may NEVER alter

A width change may re-arrange a screen. It may never re-design it. These are the things that must be identical at every width; everything after this section is about what is ALLOWED to change.

1. **Every width gets the same content — never a stripped-down "mobile version."** Whatever a desktop user can read or do, a phone user can read or do. Research consistently shows mobile users attempt every task desktop users do; hiding features or data on small screens just strands them. Deferring content behind a clearly labeled disclosure (an "expand" control, a tab) is legitimate; deleting it from a width is a defect. — [NN/g content parity, Baymard mobile commerce research] — [mechanical]
2. **The phone's top-to-bottom order IS the priority ranking, and every wider layout must preserve it.** A single column forces you to rank zones honestly — first thing shown = most important. When width lets zones sit side-by-side, the reading order (top-left toward bottom-right in LTR) must still walk that same ranking. If the desktop arrangement implies a different importance order than the phone stack, one of them is lying. — [Material 3 canonical layouts, NN/g F-pattern, content-first consensus] — [judgment]
3. **Terminology, labels, and microcopy are identical at every width.** A button called "Log workout" on the phone is "Log workout" on desktop — never "Add session." Abbreviating a label ONLY when space forces it is a last resort and the abbreviation must stay self-explanatory (house copy rule). Renaming between widths makes users think they're different features. — [NN/g consistency, house copy rules] — [mechanical]
4. **Grouping logic is identical at every width — reflow moves whole groups, never splits them.** Items that belong together on the phone (a value and its label, a set of related stats, a zone's heading and its content) stay together at every width. Reflow rearranges the groups relative to each other; it never scatters a group's members into different regions of the screen. — [Gestalt proximity (north star), Material 3 adaptive design] — [mechanical]
5. **One visual model, one component set, one token set — at every width.** Phone and desktop are the same design rendered at different sizes, not two designs. Same shared components, same type ramp, same color tokens, same iconography, same spacing scale (per-breakpoint token VALUES may differ — ux-canon 04 §28 — but the scale is one scale). A desktop that grows cards where the phone was cardless, or vice versa, violates both this rule and the north star, which applies at all widths. — [Material 3 ("one app, adapted"), Apple HIG layout, house north star] — [mechanical]
6. **Every interaction reachable at one width is reachable at all widths.** No action may exist only behind hover (desktop-only) or only behind a gesture (phone-only). Hover and gesture are accelerators layered on a universally reachable control. Touch behavior specifics are ux-canon 06 §84/§86; the composition consequence here: when reflow collapses a toolbar or promotes a pane, audit that no action fell off the reachable surface at any width. — [ux-canon 06 §84 §86, Apple HIG, NN/g] — [mechanical]
7. **Source order matches visual order at every width.** Achieve reflow with layout (grid areas, flex direction), but never let CSS reordering make the DOM order disagree with what a sighted user reads — keyboard tabbing and screen readers follow the DOM, and a desktop grid that visually reorders content leaves non-visual users on a different screen. When phone and desktop genuinely need different orders, that is a signal to re-rank (see #2), not to `order:`-shuffle. — [WCAG 1.3.2 / 2.4.3, MDN grid accessibility warnings] — [mechanical]
8. **Crossing a breakpoint never loses state.** Resizing the window, rotating the phone, or a foldable posture change preserves scroll position, form input, selection, and open/closed states. A user mid-task who rotates their phone is the same user mid-task. — [Apple HIG, Android configuration-change consensus; rotation specifics in ux-canon 06 §79] — [mechanical]
9. **Data meaning is invariant even when its rendering adapts.** A visualization may simplify at narrow widths (fewer gridlines, fewer tick labels, a condensed legend) but must encode the same quantities the same way — same scale type, same mapping, same numbers. "Prettier may not mean vaguer" (north star goal 4) applies per-width too: the phone rendering may not be a vaguer chart than the desktop one. — [north star goal 4, dataviz consensus (Few, Tufte)] — [judgment]

## B. Reflow grammar — the standard transformations as width grows

The consensus transformations. Everything here is a conditional vocabulary — which transformation applies depends on the content relationship, and that condition is stated in each rule.

10. **Single column is the root form; width adds columns by promoting stacked zones to side-by-side — never by inventing new zones.** The canonical adaptive move, across Material 3, Apple HIG, and the responsive-web literature, is: what stacks at compact sits adjacent at expanded. The set of zones is fixed by the content (see #1); width only changes their arrangement. — [Material 3 canonical layouts, responsive-design consensus] — [mechanical]
11. **Promote zones to side-by-side only when they are semantically parallel or one supports the other — never to fill width.** Two zones may share a row when they are peers (two macro stats), or when one is context for the other (a chart and its summary). Placing unrelated zones adjacent because the width existed creates false relationships — proximity implies meaning (Gestalt). If nothing qualifies, keep the column and let the margins grow (see #25). — [Gestalt proximity, Material 3 supporting-pane layout] — [judgment]
12. **Reflow works at the zone level first; elements inside a zone keep their internal arrangement as long as possible.** As width grows, re-arrange the big pieces (zones) before restructuring within them. A zone whose internal layout is redesigned at every breakpoint multiplies verification surface and drifts from its siblings; a zone that holds its internal shape while the page re-tiles around it stays recognizable. Container queries (see #45) are the mechanism: the zone adapts to ITS width, wherever the page puts it. — [component-driven responsive consensus, Every Layout] — [judgment]
13. **A row of peers wraps as a unit: all side-by-side or all stacked, never one orphan.** When peer items (stat trio, action pair, feature columns) no longer fit in a row, they should all drop to a stack rather than leaving two up and one squeezed below — the half-wrapped state reads as broken. This is the Every Layout "Switcher" behavior: layout flips wholesale at a content-driven threshold. Exception: a deliberately wrapping GRID of many uniform items (a gallery) wraps row by row by design. — [Every Layout (Switcher), intrinsic-design consensus] — [mechanical]
14. **Full-width actions on phone become intrinsic-width actions inline on desktop.** At compact widths, primary buttons legitimately run full-width (easy thumb target, clear terminus). At wide widths a full-width button is a defect — a 1000px button is absurd; buttons return to hugging their label plus padding, placed by convention (form-end, dialog-corner). The transformation is width-of-container → width-of-content. — [Baymard mobile forms, ux-canon 04 §26, platform button conventions] — [mechanical]
15. **List → list-detail is the standard wide transformation for browse-and-inspect content.** On the phone, tapping a list item navigates to a detail screen; at expanded widths and up, list and detail sit side-by-side and selection swaps the detail pane in place. Use it when users flip between items frequently (history, messages, exercise library); don't force it on lists whose items are visited once. Selection state must be visible in the list when the pane is present. — [Material 3 canonical layout: list-detail, Apple HIG split views] — [judgment]
16. **Hidden-on-phone (behind a tap) → persistent-on-desktop (a pane) is the standard promotion for supporting content.** Filters in a bottom sheet, details behind a disclosure, a secondary panel behind a button: when width allows, show them persistently beside the primary content instead of behind interaction. The inverse holds when narrowing: a desktop side pane collapses to an on-demand surface, never to nothing (see #1). — [Material 3 canonical layout: supporting pane, progressive disclosure consensus] — [judgment]
17. **A feed or gallery of uniform items adds columns with width; item size stays in a legible band.** Uniform collections (workout history entries, photos, exercise cards) are the one place width straightforwardly buys more columns: 1 at compact, 2–3 at medium/expanded, more beyond — implemented fluidly (auto-fit with a min item width), not with hand-set per-breakpoint counts. Items should stay near one legible size rather than inflating to fill; add columns, don't inflate cells. — [Material 3 canonical layout: feed, CSS grid auto-fit consensus] — [mechanical]
18. **Forms stay single-column at every width; width caps the form instead of multiplying columns.** Multi-column forms cause skipped fields and wrong completion order at any width. On desktop, a form gets a max-width (roughly 400–600px for typical field stacks) and left-anchors to the page's content edge per forms canon 03 #38 (the canonical statement) — it centers only when the whole screen is a centered composition, and it never spreads into columns. Exception: tightly-bound short pairs (city + postcode, month + year) may share a row at any width where they fit. — [Baymard form research, Luke Wroblewski, NN/g; forms canon 03 #38] — [mechanical] *(patched 2026-07-23: "centers or left-anchors" resolved via 03 #38)*
19. **Tables reflow deliberately: fewer columns, stacked rows, or in-container horizontal scroll — never page overflow, never silently dropped data.** At narrow widths a many-column table must choose: hide low-priority columns behind an expand/detail affordance, restructure each row into a stacked block, or scroll horizontally INSIDE its own container with a visible cue. The chooser, by content: columns users compare ACROSS rows (weights over sessions) → in-container scroll with the identity column pinned; record-shaped rows each read alone (one entity per row) → stacked blocks; genuinely tertiary columns consulted rarely → hide behind the row's detail/expand. Decide once per table type in the shared component, not per screen. Letting the table stretch the page (overflow) or quietly amputating columns (violates #1) are the two failure modes. — [Baymard mobile tables, responsive-table consensus, ux-canon 04 §30] — [mechanical] *(patched 2026-07-23: per-strategy decision conditions added per sweep THIN #3)*
20. **Images and scene compositions scale fluidly with preserved aspect ratio; art-direction crops may change framing, never subject.** Media sizes with its container (`max-width:100%`, explicit aspect-ratio to prevent shift — ux-canon 06 §36). Serving a tighter crop at narrow widths (`<picture>` art direction) is legitimate; swapping to a different image or dropping the scene at some widths breaks the one-visual-model rule (#5). North-star scene zones (jug, sleep orbit) must be composed to survive the full width range or given per-class crops designed together. — [MDN responsive images, north star scene-based presentation] — [judgment]
21. **Navigation reflows along the standard chain (bottom bar ↔ rail ↔ drawer), owned by the navigation file — the composition rule here is that content layout and nav layout change together at the same threshold.** When the nav moves from bottom bar to side rail, the content area's width and margins change; pick one breakpoint for both so the screen re-arranges once, not twice in quick succession. — [Material 3 navigation guidance; nav pattern choice is canon 02's domain] — [mechanical]

## C. What extra width buys — content, whitespace, and the measure

22. **Cap the reading measure: body text never exceeds roughly 45–75 characters per line, no matter the window.** This is the oldest rule in the file and the most violated on the web: prose spanning a 1280px window is unreadable — the eye loses the line on the return trip. Give every text block a max-width in `ch` units (≈65ch is the classic ideal) and let the margins take the remaining width. A phone layout stretched to desktop fails this rule first. — [Bringhurst, Butterick's Practical Typography, NN/g line length] — [mechanical]
23. **The choose rule: extra width buys MORE VISIBLE CONTENT when the job is scanning or comparing; it buys MARGIN AND MEASURE when the job is reading or completing one task.** Feeds, lists, histories, galleries, data tables → use the width for more columns/rows in view (fewer scrolls, easier comparison). Prose, forms, focused flows, a single scene → cap the content width, center or anchor it, and let whitespace absorb the rest. Decide per zone, not per page: one screen can hold a capped reading zone beside a width-hungry data zone. — [NN/g content density research, Material 3 (pane expansion vs. fixed panes), Baymard] — [judgment]
24. **Desktop may densify within the token scale — never below the floors.** More rows in view, tighter per-breakpoint spacing tokens, compact table paddings (ux-canon 04 §28, §34) are how desktop earns its width for data surfaces. What density may never do: shrink type below the house 12px floor, shrink touch/click targets below ux-canon 06 §82 numbers, or introduce a compact variant component the phone doesn't share (#5). — [Material 3 density, house 12px floor, ux-canon 04 §34] — [mechanical]
25. **Empty margin is a valid use of width; stretched content is not.** When no zone qualifies for promotion (#11) and the content is capped (#22), the honest desktop layout is a centered or left-anchored column with generous margins. Resist the itch to fill: padding a screen with decorative panels, oversized imagery, or invented widgets to "use the space" adds noise, violates content parity in reverse, and — as tiles — walks straight into the north star's anti-goals. — [NN/g white space, Refactoring UI ("don't stretch to fill"), house north star anti-goals] — [judgment]
26. **Fluid type scales the display sizes modestly and leaves body size nearly constant.** Headlines and hero numerals may step up with width (CSS `clamp()` between a phone floor and desktop cap); body text stays ~16–18px at every width — bigger windows do not mean bigger paragraphs, they mean more margin (#22). Fluid values must have explicit floors and caps; unbounded viewport-unit type breaks at both extremes and can break user zoom. — [modern fluid-typography consensus (clamp), WCAG resize concerns, ux-canon 04 §1] — [mechanical]
27. **Pick one page max-width token and apply it everywhere; full-bleed is reserved for backdrop and shell.** The content column caps at a single house value (commonly ~1100–1400px) and centers beyond it, identically on every surface — per-page maximums drift into inconsistency. Backgrounds, atmosphere, dividers, and the nav shell may run edge-to-edge behind and around the capped column; the north star's continuous background is exactly this: full-bleed atmosphere, capped content. — [design-system consensus, ux-canon 04 §26 §28, north star connective tissue] — [mechanical]

## D. Phone composition (~320–599px)

28. **One dominant column, one alignment spine.** At compact widths every zone resolves to a single strong left edge (LTR); content that wanders between left-aligned, centered, and indented reads as broken at 384px where there's no room for the eye to forgive. Centered text is the exception for display moments (hero numerals, empty states), deliberately, not by drift. — [ux-canon 04 §24, NN/g mobile scanning, Refactoring UI] — [mechanical]
29. **The inset decision: text and controls sit inside the page margin; only backdrop, media, and full-width separators go edge-to-edge.** The phone page margin is the house token `--gutter` (24px minimum at phone widths — the APPROVED ds.css value; 16px is the wider industry default, but the token wins). Insets beyond the gutter follow the one horizontal-budget arithmetic in 02 #13. Edge-to-edge is earned by immersive content — a scene, a photo, a chart's backdrop, the continuous background — and by the nav shell. Body text touching the screen edge is a defect; so is an interactive control whose hit area gets clipped by the viewport. — [Material 3 layout (margins), Apple HIG layout, north star scene zones; APPROVED ds.css `--gutter`, 02 #13] — [mechanical] *(patched 2026-07-23: 16px default replaced by the --gutter token)*
30. **At compact width, side-by-side is reserved for tightly-bound pairs; everything else stacks.** A value+label, an icon+line of text, two peer stats — these may share a row at 320–384px if both survive long content (test with real long values). Unrelated zones never share a row at compact; the width can't afford false adjacency. — [Gestalt proximity, mobile-first consensus] — [judgment]
31. **The first phone viewport answers the surface's central question and shows its primary action.** At ~384×~700 CSS px, before any scroll: what this screen is, today's key state, and the one thing to do (north star five-second goal). Decoration that pushes the answer below the first viewport at 320–390px is mis-spent space. This is where the priority ranking (#2) is proven. — [north star measurable goals, NN/g above-the-fold research] — [judgment]
32. **Horizontal scrolling earns its place almost nowhere; a swipeable row must meet ALL the conditions.** The page never scrolls sideways (ux-canon 06 §77). An internal horizontally-scrolling row (carousel/chip row) is acceptable only when: items are uniform peers (not mixed content), the next item visibly peeks so scrollability is self-evident, the row is an optional browse (nothing critical lives ONLY off-screen right — see #1), and scroll position isn't the only way to reach the content elsewhere in the app. Auto-rotating carousels are rejected outright. Anything failing a condition becomes a vertical list or a "See all" link. — [NN/g carousels, Baymard horizontal scrolling research] — [mechanical]
33. **Budget sticky chrome: persistent header plus at most one persistent bottom element, together within the canonical ~25% viewport cap (02 #29 — the one number; this rule cites it).** Every sticky bar shrinks the world's smallest canvas; a sticky header + sticky tab bar + sticky CTA + keyboard leaves a letterbox. Prefer collapsing headers (shrink or hide on scroll-down, return on scroll-up) and context-summoned CTAs; the pinned-edge stacking order is 08 §J. Keyboard/safe-area interactions of fixed bars are ux-canon 06 §75/§92. — [Apple HIG (content deference), mobile viewport-share consensus; 02 #29] — [judgment] *(patched 2026-07-23: "under a third" unified to 02 #29's 25% cap)*
34. **Compose the 320px case as a valid layout, not a survival mode.** 320 (WCAG reflow width, small phones, split-screen) gets the same composition as 384 with tighter margins — nothing clipped, no overlap, labels intact. If a zone only works ≥360px, the zone is over-specified; redesign the zone, don't gate the width. House rule: 320 is a spot-check width in every visual verification. — [WCAG 1.4.10 reflow, house verification rule] — [mechanical]
35. **Long-content phone screens prioritize ruthlessly downward, never sideways and never away.** The compact answer to "too much content" is order + progressive disclosure within the column (summaries that expand, "Show all" thresholds on long lists) — not horizontal panes, not hiding (violates #1), not tiny type (violates the floor). — [progressive disclosure consensus (NN/g), content-parity rule #1] — [judgment]

## E. Desktop composition

36. **A desktop page is composed FOR the width, not survived AT it.** The two canonical failures: the phone stack stretched to 1280px (absurd measures, football-field buttons, a thin ribbon of content in a void with no structure) and the crushed-desktop phone page. If a surface ships with side-by-side zones on desktop that are merely the phone stack with `flex-direction: row` slapped on, nobody composed it. Every surface gets a deliberate answer to "what does the expanded arrangement look like?" even when the answer is "the capped column, centered" (#25). — [responsive-design consensus, Material 3 canonical layouts] — [judgment]
37. **Multi-zone desktop arrangements keep a dominant primary region; supporting zones flank it.** When zones sit side-by-side, the primary zone reads first and largest — roughly a 2:1 presence over a supporting pane rather than equal halves — unless the zones are genuine peers (then equal treatment is honest). Equal-width thirds of unequal-importance content flatten the hierarchy the phone stack made clear. — [Material 3 supporting-pane proportions, visual-hierarchy consensus] — [judgment]
38. **The desktop arrangement must not decay into a tile dashboard.** Width makes the card-grid temptation strongest: N zones, N boxes, snap to grid, done. The north star forbids this at ALL widths — desktop zones are separated by the same means as phone zones (whitespace, alignment, scale, atmosphere, density shifts, subtle dividers), arranged on an invisible grid, never exposed AS a grid of containers. The escape hatch (container as last resort) is the same escape hatch, no wider on desktop. — [house north star (applies at all widths), Stripe precedent cited therein] — [judgment]
39. **Use persistent panes to remove navigation round-trips when the user flips between items or needs both at once.** The desktop's structural advantage is showing two related things simultaneously (list-detail #15, supporting pane #16, content + persistent filters). Apply it when the phone flow demonstrably ping-pongs (back-and-forth between list and detail); leave single-focus flows (setup, checkout-style sequences, a workout in progress) single-focus at every width — width is not a reason to split attention. — [Material 3 canonical layouts, Apple HIG split view, NN/g workflow research] — [judgment]
40. **Desktop reveals more, but hover and pointer precision unlock nothing exclusive.** Showing secondary info persistently that the phone puts behind a tap: good (#16). Making any action or information reachable ONLY via hover, right-click, or fine-pointer interaction: forbidden — desktop users on touch laptops, keyboard users, and the phone parity rule (#6) all break. Hover may enrich (previews, shortcuts); it may never gate. — [ux-canon 06 §86, WCAG pointer/keyboard consensus] — [mechanical]
41. **Wide-viewport atmosphere stays continuous; zones bleed, backgrounds run.** The north star's connective tissue (continuous background, zone atmospheres bleeding into neighbors) is easiest to lose on desktop, where zones sit beside each other: side-by-side zones need the same atmospheric continuity horizontally that the phone stack has vertically, or the page falls apart into panels. Backdrop runs full-bleed behind the capped content column (#27). — [house north star (connective tissue), figure-ground composition] — [judgment]

## F. Breakpoint discipline

42. **Fluid-first: the layout must be correct at EVERY width, and breakpoints are corrections at the few places fluid behavior isn't enough.** Design with intrinsically flexible primitives — wrapping flex, grid `auto-fit`/`minmax()`, `clamp()`, `ch`-based max-widths — so the layout negotiates its own width continuously. A breakpoint is where you change the RULES (promote a pane, flip a switcher); between breakpoints everything must already be right. Anything correct only AT the tested widths is broken, just unobserved. — [Jen Simmons (intrinsic web design), Every Layout, ux-canon 04 §25] — [mechanical]
43. **Breakpoints live where the content breaks, not where devices are.** Set each threshold by resizing until the layout fails (measure exceeded, row cramped, pane too thin) and breaking there. Device-model breakpoints are obsolete — foldables, split-screen, and desktop windows put every width in play. (Restates ux-canon 06 §78 for composition; that file owns the device-targeting prohibition.) — [ux-canon 06 §78, responsive consensus, Material window-class rationale] — [mechanical]
44. **Use the Material 3 window-size classes as shared vocabulary and design checkpoints, not as the only widths that exist.** Compact (<600dp), medium (600–839), expanded (840–1199), large (1200–1599), extra-large (1600+) — verified current as of mid-2026 — give sessions a common language ("this pane appears at expanded") and a checklist of arrangements to design. They do not replace content-driven thresholds (#43) or fluidity between them (#42). House verification widths (320/360/390/768/1024/1280) sample all the classes that matter here. — [Material 3 window size classes (m3.material.io, verified 2026-07), house smoke-test widths] — [mechanical]
45. **Components adapt to their CONTAINER, not the viewport.** A zone placed in a desktop side pane may be narrower than the same zone full-width on a phone; viewport-based styling gets it wrong in exactly that case. Container queries are baseline-supported in all browsers (since 2023) and are the standard mechanism in 2026: the page decides zone arrangement by viewport/class, each zone decides its internal layout by its own width. This is what makes #12 buildable. — [CSS container queries (baseline), component-driven consensus, MDN] — [mechanical]
46. **Prefer few breakpoints; every breakpoint is a layout you must verify forever.** Each `@media`/`@container` rule adds a permanent state to test at every future change. The intrinsic toolbox (#42) exists to make most of them unnecessary; a surface needing more than two or three rule-changing thresholds is usually over-arranged. — [Every Layout ("algorithms, not magic numbers"), maintenance consensus] — [judgment]
47. **Design the compact and expanded arrangements together, from a content priority list — never "port later."** The reliable process: rank the content (that ranking is the phone stack AND the desktop reading order, #2), then compose both arrangements from it in the same session. Desktop-later yields stretched phone pages; phone-later yields crushed desktops; both are the failure this canon exists to prevent. — [content-first consensus (mobile-first literature), Material 3 adaptive process] — [judgment]
48. **One DOM for all widths; layout divergence lives in CSS.** Duplicated per-width DOM branches (`<div class="mobile-only">` twins) drift apart, double the content-parity audit, ship dead weight, and confuse assistive tech. JS width-sniffing for layout is a last resort for genuinely different interaction machinery (a pointer-driven vs touch-driven widget), not for arrangement. — [responsive consensus, progressive-enhancement consensus] — [mechanical]

## G. Mechanical verification — the reflow checks every surface must pass

Overlapping behavior checks (overflow, safe areas, font scaling, keyboards) are owned by ux-canon 06 §J; these are the composition-specific checks.

49. **Zero horizontal page overflow at every width from 320px up** — the page body never scrolls sideways; wide content scrolls inside its own container. (Owned by ux-canon 06 §77 and 04 §30; listed here because it is this file's first gate.) Check by resizing continuously, not sampling. — [ux-canon 06 §77, WCAG 1.4.10] — [mechanical]
50. **Nothing clipped, overlapped, or involuntarily truncated at 320–384px.** Every label, value, input, and button fully visible with real content — including the long values the surface can actually hold (longest exercise name, 4-digit weights, widest date string). Ellipsis appears only where a deliberate truncation policy exists AND the full value is reachable (tap, detail, tooltip-equivalent). — [house verification rule, Baymard truncation research] — [mechanical]
51. **Tap/click targets survive reflow at every width.** The moment two stacked full-width controls become one inline row, their targets shrink — re-verify ux-canon 06 §82's minimums (44×44pt / 48×48dp, ~8px gaps) at the tightest width of every arrangement, not just at the design widths. — [ux-canon 06 §82] — [mechanical]
52. **No text block's rendered line exceeds ~75–80 characters at any width.** Sample the widest window state; any prose or multi-line UI text past the measure cap means a missing max-width (#22). Automatable: computed width / average glyph width, or flag text blocks lacking a max-width in `ch`/px. — [Bringhurst, NN/g line length] — [mechanical]
53. **The priority-order walk: enumerate the zones top-to-bottom on the phone, then walk the desktop arrangement in reading order — the sequences must match.** Five-minute manual check per surface (#2). If desktop reading order visits zones in a different rank order, the arrangement (or the ranking) is wrong. — [content-first consensus] — [judgment]
54. **The continuous-drag test: resize 320 → 1280 in one slow drag; every intermediate state is a presentable layout.** Watch for the between-breakpoint failures sampling misses: cramped rows just before a switch threshold, orphan wraps (#13), panes squeezed below usability just after they appear, jumping content. The house smoke test samples six widths; this drag covers the gaps between them. — [intrinsic-design consensus (#42), house six-width smoke test] — [mechanical]
55. **400% browser zoom at 1280 (= 320px CSS width) reflows to the single-column arrangement with no loss of content or function.** This is WCAG 1.4.10 verbatim and doubles as proof that the compact arrangement is real, not device-sniffed. — [WCAG 1.4.10 reflow] — [mechanical]
56. **The standard house evidence: screenshots at 360, 390, and desktop, with a 320 spot-check when the layout is dense — actually inspected, per surface changed.** (House rule, CLAUDE.md §4; restated as this file's exit gate.) A fluid layout right at 360 and 390 is right between them (#42) — but only if it is actually fluid, which #54 verifies. — [house CLAUDE.md §4] — [mechanical]
57. **Landscape phone / split-screen (~600–840px medium widths) renders a working arrangement, not a stretched compact or broken half-desktop.** Medium is the most-skipped class and exactly where foldables and split-screen live; the house 768 smoke width samples it, and rotation must preserve state (ux-canon 06 §79). — [Material 3 medium class, ux-canon 06 §79] — [mechanical]

## Contested / no-consensus (excluded from the numbered canon)

- **Exact ideal measure** — 45–75ch (Bringhurst) vs 50–60 (some NN/g guidance) vs up to ~90 (Butterick's outer bound). Consensus exists that a cap must exist and that full-window prose fails; the precise number is a house-token decision. The canon states the union band (#22, #52). [contested on the number, not the rule]
- **Mobile-first vs desktop-first CSS authoring order** — content-first process (#47) is consensus; whether the stylesheet's base case should be the narrow or wide layout is tooling preference with no user-visible stake. [no consensus]
- **Container queries replacing media queries entirely** — 2026 practice treats them as complements (page arrangement = viewport/media, component internals = container); "container-only" architectures exist but are not consensus. The canon takes the complement position (#45). [contested beyond that]
- **Horizontal carousels on mobile at all** — NN/g is broadly negative (especially auto-rotating, which is consensus-rejected); Baymard accepts curated manual rows in specific commerce contexts. The canon's conditional (#32) is the overlap; the wider "are swipe rows ever good UX" fight is unresolved. [contested]
- **Two-column desktop forms for long related field sets** — Baymard and Luke W say single-column, period; several enterprise design systems permit grouped two-column sections for expert data-entry screens. Canon takes single-column with the bound-pair exception (#18); the enterprise carve-out is unproven for consumer products like this one. [contested]
- **Importing M3 dp breakpoints directly as web px breakpoints** — M3's classes are Android dp semantics; on the web, content-driven thresholds (#43) take precedence and the classes are vocabulary (#44). Some teams hard-code 600/840/1200 as px media queries; harmless in practice but not a standard. [no consensus]
- **Sticky-chrome viewport-share limit** — no research source publishes a number; the direction (minimize persistent chrome on phones) is consensus, the threshold is house judgment. #33 now defers to the canonical 25% cap in comp-canon 02 #29 (patched 2026-07-23) — that number is the house pick, not industry law. [contested on the number]
- **Whether desktop information density should exceed mobile at all for consumer (non-enterprise) products** — enterprise systems (Carbon, Fluent) publish density modes; consumer-app consensus leans "same airy density, more columns." Canon permits token-level densification for data surfaces only (#24). [contested]
