# Composition Canon 02 — Information Density and Breathing Room

Domain: how much content a screen carries and how tightly it is packed — density as a per-context decision, the phone-space economy at ~384px, content-per-viewport rules, whitespace as a structural tool, screen-level measure, and progressive disclosure as the pressure valve. This is the screen-level layer ABOVE the element-level spacing law in UX Canon 04 §2 (spacing scale #21, proximity #23, gutters #28, vertical rhythm #33, density-per-surface #34, nesting cap #36) — those rules are referenced here by number, not restated.

Tag key: **[mechanical]** = checkable by rule/tool with no taste required. **[judgment]** = requires a human (or design-trained) eye, but the direction of "better" is agreed.

Sources abbreviated: RUI = Refactoring UI (Wathan/Schoger); M3 = Material Design 3 (incl. its density system); HIG = Apple Human Interface Guidelines (incl. watchOS/CarPlay glanceability guidance); NN/g = Nielsen Norman Group; Baymard = Baymard Institute e-commerce research; Tufte = Edward Tufte (data-ink, small multiples); Few = Stephen Few (dashboard design); Carbon = IBM Carbon Design System; Fluent = Microsoft Fluent 2; Polaris = Shopify Polaris; VWIG = Vercel Web Interface Guidelines; WCAG = WCAG 2.1/2.2. House = this project's north star (`design-north-star-2026-07-16.md`) and owner decisions.

House context that binds everything below: the product is a fitness app used mid-workout on a ~384px phone, built as a continuous cardless information surface with editorial hierarchy (north star). Cardless composition is itself a density technology — every container border and its padding that the north star removes returns pixels to content. The rules below assume that direction.

---

## 1. Density Is a Decision Made Per Screen Type, Never a Default

1. **Choose each screen's density from its task, and write the choice down — never inherit density from whatever component was pasted first.** Plain English: before laying out a screen, answer "is the user glancing, working, reading, or feeling?" and pick tight/medium/airy accordingly; a screen that never made this decision gets whatever density its first component happened to have, which is how the same app ends up cramped in one place and empty in another. [M3 density ("density is a deliberate choice for data-rich contexts"), Carbon (productive vs. expressive moments), UX Canon 04 #34] [judgment]
2. **The more urgent and repeated the task, the denser the screen; the more emotional or one-time the moment, the airier.** Plain English: rank screens on two axes — how often the user hits it, and how much they're "doing" vs. "feeling." Set logging (hit 20× per workout, mid-effort) earns maximum glanceable density. A workout-complete celebration or onboarding step (once, emotional) earns generous air. History browsing sits between. When a new screen type appears, place it on those two axes and the density answer falls out. [NN/g (task-focused vs. experience-focused design), Carbon productive/expressive, HIG (celebratory moments), RUI] [judgment]
3. **If the user's hands or attention are compromised while using a screen, increase target size and datum size, and cut item count — density buys nothing a shaking hand can't hit.** Plain English: mid-set, the user is sweaty, breathing hard, phone at arm's length, possibly gloved. For any surface used in motion or mid-effort, the priority order is: bigger touch targets, bigger key numbers, fewer things — even at the cost of scrolling for secondary info. Density on in-motion screens means fewer, larger elements packed with meaning, not more, smaller elements. [HIG (CarPlay/watchOS: design for divided attention), NHTSA glance guidance (interactions decomposable into ~2-second glances), NN/g glanceability] [judgment]
4. **When a screen serves both a working mode and a reviewing mode, design two densities and switch on mode — don't average them.** Plain English: a workout screen during the workout (glance mode: huge current-set numbers) and the same data after the workout (review mode: compact table of all sets) have different right answers. A single compromise density fails both. If both modes exist, the screen changes density with the mode. [Few (dashboard vs. analysis modes), M3 density levels, Fluent (density per surface context)] [judgment]
5. **Expert-frequency surfaces may run denser than first-run comfort suggests; first-run surfaces may not.** Plain English: a screen the user will see hundreds of times (daily log) can be information-dense because the user learns its layout — repeated exposure amortizes the learning cost. A screen most users see once (onboarding, permission ask, empty state) must be instantly parseable with zero learning, which means low density. Decide by exposure count, not by how it demos. [NN/g (learnability vs. efficiency trade-off), Carbon/Fluent (compact modes aimed at expert/enterprise use), Baymard (first-visit comprehension)] [judgment]
6. **Dense is not the same as cramped: density is high information per pixel; cramped is high ink per pixel.** Plain English: the goal of a dense screen is more *meaning* per glance — achieved by removing chrome (borders, redundant labels, decoration) before shrinking gaps. If a screen feels crowded, first delete non-data ink (UX Canon 04 #90's data-ink rule applied to whole screens); only then consider whether spacing must tighten. Shrinking gaps around clutter produces cramped; deleting clutter often makes the same content feel airy at the same size. [Tufte (data-ink ratio; "to clarify, add detail" — detail, not decoration), RUI (remove borders before adding space), House north star (cardless = chrome removal)] [judgment]
7. **When in doubt between two densities, prototype the denser one with chrome removed before accepting the airier one with chrome kept.** Plain English: the lazy resolution of "this feels tight" is adding space and pushing content below the fold. The better first move is stripping containers, merging redundant labels, and letting typography group (north star's whole thesis). Only if the stripped version still feels tight does the screen earn more air. [Tufte, RUI, House north star] [judgment]

## 2. Glance vs. Read: Density by Attention Mode

8. **A glance surface must answer its one question in under ~2 seconds without scrolling or tapping; design backwards from that.** Plain English: for any screen used mid-task (current set, rest timer, today's next action), name the single question it answers ("what weight/reps now?", "how long left?"). Everything needed for that answer is visible, large, and high-contrast in the first viewport; everything else is subordinate or elsewhere. If answering requires scroll, tap, or reading a sentence, the surface has failed as a glance surface regardless of how complete it is. [HIG watchOS ("glanceable: useful information at a glance"), NHTSA 2-second glance standard, NN/g glanceability, North star goal #1 (five-second understanding is the ceiling for the whole screen; glance elements are faster)] [judgment]
9. **On a glance surface, the key datum outweighs everything else by an order of magnitude — one hero number, not four peers.** Plain English: glance reading works by preattentive pop-out: one value so much bigger/bolder than its neighbors that the eye lands on it without searching. Four equally-weighted stats force a search, which is reading, not glancing. If a glance surface has more than one hero, demote until one remains. [Few (dashboard "one thing that matters"), NN/g eyetracking (scanning locks onto dominant elements), RUI (hierarchy by de-emphasis, UX Canon 04 #51), House north star (editorial hierarchy)] [judgment]
10. **Read surfaces (history, plans, explanations) may be long and scrolling, but must be scannable: front-loaded structure every viewport.** Plain English: when the user is seated and reading, length is fine — but each viewport-height of a scrolling read surface needs its own visible structure (a heading, a hero datum, a zone shift) so a scroller always knows where they are. A viewport of undifferentiated rows is where scanning dies. [NN/g (F-pattern scanning; users scan, not read), UX Canon 04 #56, #156] [judgment]
11. **Never mix modes within one viewport: a glance element floating inside a read layout gets lost, and a paragraph inside a glance layout gets skipped.** Plain English: if a screen needs both (e.g., today's hero action plus explanatory prose), zone them vertically — glance zone first and self-sufficient, read zone after, with a clear macro break between (see §6). Interleaving big glanceable numbers with sentences makes both illegible. [NN/g (mixed content patterns break scanning), Few, House north star (semantic zones)] [judgment]
12. **Numbers a user compares must sit within one eye-span; if comparison matters, densify until compared values are simultaneously visible.** Plain English: "did I beat last week?" only works if this week's and last week's numbers are on-screen together — comparison across a scroll or a tap is done from memory and fails. When the screen's job is comparison, tighten it until the compared set fits one viewport; when it can't fit, summarize the comparison into a delta ("+5 lb vs last time") rather than making the user scroll-and-remember. [Tufte (comparisons within the eye-span; small multiples), Few, NN/g (working-memory limits), UX Canon 04 #96] [mechanical]

## 3. The Phone-Space Economy: Horizontal Budget at 384px

13. **Budget horizontal insets token-relatively: at phone widths the base rent is the page margin `--gutter` (24px minimum at phone widths, per the APPROVED ds.css); beyond it, at most ONE additional left inset anywhere in the stack — one structural indent level (#15) OR one earned container's padding (01 §4) — never both, and never stacked containers.** Plain English: every pixel of left padding is rent paid on every single row of the screen. `--gutter` is the necessary base; after that, exactly one more inset may exist, and it must be saying something (subordination, or an earned container that pays its rent knowingly — 01 #59). Two nested 16px-padded containers inside the gutter (24+16+16 = 56px per side = 112px of a 384px phone = 29% gone) is the classic cards-in-cards defect this rule exists to kill. Audit by measuring from screen edge to the leftmost content glyph: it sits at `--gutter`, or at `--gutter` plus one stated inset. This is the ONE horizontal-budget arithmetic for the whole canon; 01 #59 and 07 #29 cite it. [RUI (nesting waste), M3/HIG (single page margin), House north star, APPROVED ds.css `--gutter`, UX Canon 04 #28, #36] [mechanical] *(patched 2026-07-23: rewritten token-relative; old ≤24px cap contradicted --gutter)*
14. **Content-bearing containers at phone width are full-bleed-to-margin by default; any container narrower than the page margin's content column must justify its indent with a stated meaning.** Plain English: on the continuous surface, content aligns to one strong left edge at the page margin (UX Canon 04 #24). An element indented past that edge is *saying something* — "I am subordinate to the thing above" (e.g., a set row under an exercise name). If the indent isn't saying that, it's just lost width; remove it. [RUI (alignment edges), NN/g (indentation encodes hierarchy), House north star (grid for alignment, not visible containment)] [judgment]
15. **Indentation as hierarchy costs width on every descendant row — one indent level is the default on phones, two is the hard maximum anywhere, and the step is the one token `--sp-4` (16px); encode deeper hierarchy with typography instead.** Plain English: an outline with three indent levels burns 48px before content starts. On a phone, show the first level of nesting by indent and every deeper level by type (size/weight/color per UX Canon 04 #8, #52) at the same left edge; a second indent level is a desktop affordance or a justified exception, never a phone default. Same rule, same step token, as 06 #28 — one statement of the indent law. [RUI, NN/g (deep visual nesting on mobile), UX Canon 04 #36; 06 #28] [mechanical] *(patched 2026-07-23: aligned with 06 #28 — one default, two max, 16px step)*
16. **Horizontal padding inside tappable rows counts against the budget too: row content aligns to the page edge, and the tap target extends invisibly full-bleed.** Plain English: a list row shouldn't inset its text 16px inside a container that's already 16px from the screen edge just to make the tap highlight look padded. Put the text on the page's content edge; let the touch target and its pressed-state highlight run edge-to-edge (bleeding wider than the text). Target size is met without renting content width. [HIG (full-width table rows), M3 (list items bleed, content aligns to keylines), VWIG] [mechanical]
17. **Never spend width on decoration at phone sizes: leading icons, avatars, and bullets in rows must earn their column or be cut.** Plain English: a 24px icon plus 12px gap in front of every list row is a 36px column — ~10% of the phone — purchased on every row. Keep it only when the icon is the recognition key (exercise thumbnails users identify by image); cut it when it's ornamental repetition (the same dumbbell glyph on every row says nothing). UX Canon 04 #77's icons-as-bullets rule, applied economically. [RUI, NN/g (redundant icons ignored), UX Canon 04 #77] [judgment]
18. **When a horizontal set of values doesn't fit at 320–384px, the resolution order is: shorten labels → drop tertiary values → stack vertically. Never: shrink type below floors, letter-squeeze, or side-scroll body content.** Plain English: a stat row of four values that overflows a phone gets fixed by cutting words or cutting the least important value, or by wrapping to two rows — not by dropping to 10px text (violates the permanent 12px floor, UX Canon 04 #3) and not by letting the page scroll sideways (UX Canon 04 #30). Deliberate in-container horizontal scrolling of homogeneous items (a chart, a week strip) is allowed with a visible cut-off cue; page-level side-scroll never is. [House type floor (owner order 2026-07-19), UX Canon 04 #3, #30, RUI, Baymard (truncated mobile content)] [mechanical]
19. **Symmetric side margins are the default; steal from the right margin before the left.** Plain English: the left edge is where scanning anchors (UX Canon 04 #56) — its margin is structural. When a wide element (a chart, a hero numeral) genuinely needs more than content width, let it bleed toward or past the *right* margin (or full-bleed both sides as a deliberate zone-scale gesture), but keep body content's left edge constant. Random per-element left margins destroy the screen's spine. [RUI (alignment), NN/g (F-pattern anchors left), House north star (full-bleed scenes are a zone-level move)] [judgment]

## 4. Vertical Rhythm Economics: What Deserves a Band vs. a Gap

20. **Spend vertical space by rank, from the canonical gap table (06 #8): the zone band is `--zone-gap` (56px at phone widths → 96px desktop), only between semantic zones; medium gaps `--sp-4`/`--sp-5` (16–24px) between groups within a zone; compact gaps `--sp-1`–`--sp-3` (4–12px) within a group. Three tiers, used by rank — nothing in between.** Plain English: on a cardless surface, vertical space IS the container system — so it must be spent like money. The big band is the zone boundary (training → nutrition → sleep); it appears a handful of times per screen. The medium gap separates groups inside a zone. The compact gap binds a group's own lines together. If every gap on a screen is 24px, the surface has no structure at all (see §6). Tier values are stated once, in 06 #8; this rule fixes how many *tiers* a screen uses and where. [RUI (space by relationship), M3/Carbon/Fluent (spacing ramps with semantic use), House north star, APPROVED ds.css `--zone-gap`; 06 #8, UX Canon 04 #21, #23, #33] [mechanical] *(patched 2026-07-23: 32–48px zone band corrected to --zone-gap via 06 #8)*
21. **A vertical span taller than the phone's viewport with no content in it is a defect anywhere; dead zones don't read as "premium," they read as broken.** Plain English: airy screens still put *something* meaningful in every viewport-height. If a celebration screen has one line and a button, the air around them should be composed (scaled type, atmosphere, placement) — not a default-stacked element floating in 500px of nothing. Emptiness must look designed: deliberate placement against the space, not leftover space below short content. [NN/g (users interpret blank viewports as page end or load failure), RUI, HIG] [judgment]
22. **Repeated rows the user scans in bulk (sets, history entries) run at compact rhythm: single-line rows, 4–8px internal padding, 44px minimum row height only because it is the touch floor.** Plain English: for lists whose job is "how many can I see at once," the touch-target floor is the density limit — go down to it and stop. Don't give scan-rows the double-height, two-line, breathing treatment; that treatment is for rows the user reads individually. A phone viewport should show ~8–12 compact rows, not 4 luxurious ones. [M3 density (compact for data-rich lists), Carbon/Polaris (condensed tables), Baymard (mobile list density: more products per viewport improves scanning up to legibility limits), touch floor per accessibility canon] [mechanical]
23. **Section headers are labels, not landings: an in-page header's own line plus its below-gap spends ≤ ~48px of vertical total; the space ABOVE it is the zone boundary's cost (06 #14), not the header's. Save the big editorial header treatment for the top-of-screen identity moment.** Plain English: each interior section header (the "SETS" or "THIS WEEK" overline) is overhead, repeated many times down a screen — keep it one compact line with a small gap binding it to its content (06 #14's asymmetry). The zone gap above the header is charged to the zone seam, so it does not count against this budget. The one place a header earns real vertical space is the screen's own title zone, once. Five 100px-tall section headers is 500px of chrome the phone paid for. [RUI, Few (dashboard real estate), House north star; 06 #14] [mechanical] *(patched 2026-07-23: budget scoped to line + below-gap per 06 #14)*
24. **Vertical padding inside a row must not exceed the row's own line-height; when padding outweighs content, the row is stealing viewport from its siblings.** Plain English: a 16px-tall line of text wrapped in 20px top and bottom padding is a 56px row that carries one line — the padding is 71% of the row. On working surfaces, keep row padding at or below the text's own height (e.g., 16px text, ≤12–16px total vertical padding beyond the touch floor). Marketing/celebration surfaces are exempt; logging surfaces are not. [RUI, M3 density decrements, Carbon compact rows] [mechanical]
25. **Whitespace below the last content element is the cheapest space on the screen; whitespace between the user and their answer is the most expensive. Trim from the top of the screen first.** Plain English: generous bottom padding after the final element costs nothing (it's past everything). Generous padding above the hero answer costs a scroll or a delayed glance on every visit. When a screen must lose vertical fat, take it from above and between primary content, and leave the tail. Equally: never let a tall decorative masthead push the day's answer below the fold (see #29). [NN/g (content priority above the fold), Baymard (oversized mobile headers push content off-screen), Few] [judgment]

## 5. Content per Viewport: The Fold, Scrolling, and Stuffing

26. **The first viewport of every screen must contain the screen's answer, not just its title: identity + primary datum/action visible without scrolling at 320–384×~640–700px.** Plain English: "above the fold" still matters — users allocate the majority of attention to the first viewport and decide there whether to scroll. The test at phone size: cold-open the screen; without touching it, can the user state what the screen is for AND see its single most important value or action? Title-plus-hero-image-plus-nothing fails; so does a wall of secondary chrome (filters, tabs, banners) that eats the viewport before content starts. [NN/g (fold research: dramatically more attention above the fold; "the fold still matters"), Baymard (first-viewport content on mobile), North star goal #1, UX Canon 04 #156] [mechanical]
27. **Scrolling is cheap; a tap is expensive; a scroll with no scent is worthless. Let screens be long only when each viewport hands the user a reason to continue.** Plain English: users scroll effortlessly IF the first viewport promises more (a cut-off element, a visible next heading, continuing structure). Deliberately let a zone peek above the fold's cut line — a fully "clean" fold that ends exactly at a section boundary reads as page-end and stops scrolling. Long is fine; long-and-unscented is where content goes to die. [NN/g (scrolling behavior; illusion-of-completeness research), Baymard (false floors), House north star (continuous surface with connective tissue between zones — the atmosphere bleed is scroll scent)] [judgment]
28. **A screen is overstuffed when the user must scroll to complete its PRIMARY task — secondary content below the fold is design, primary content below the fold is a defect.** Plain English: the fold-test discriminator is task, not quantity. Set logging: current exercise, target, input, and confirm all in one viewport — scrolling mid-set is overstuffing no matter how nice each element is. Workout history: entries below the fold are normal. Classify every element as needed-for-the-task or supporting; only supporting elements may live below the fold. [NN/g, Few (dashboards: the decision set fits one screen), Baymard, HIG] [judgment]
29. **Cap non-content chrome (headers, tab bars, banners, FABs, sticky anything) at ~25% of the phone viewport combined; every sticky element must re-earn its permanence per screen.** Plain English: a 56px header + 64px tab bar + 48px sticky CTA + notch insets can eat a third of a 640px viewport before content draws. Sticky elements are the most expensive pixels in the app — they charge rent on every frame of every scroll. Per screen, ask of each sticky element: does the user need this *while scrolled away from it*? If not (most banners, most headers mid-scroll), let it scroll away or collapse. This 25% figure is the canonical sticky-chrome cap; 07 #33 cites it, and the pinned-edge slot map lives in 08 §J. [Baymard (mobile chrome overhead), NN/g (sticky-header costs/benefits), HIG (content over chrome), VWIG] [mechanical] *(patched 2026-07-23: declared the one cap; 07 #33 now cites it)*
30. **The "one datum per screen" pattern is reserved for capture and celebration; never make a user page through screens to assemble information they need simultaneously.** Plain English: full-screen-per-question is right for onboarding inputs (one decision, big target, no distraction) and for milestone moments. It is wrong for information display: if the user needs weight AND reps AND last-time's numbers to decide, splitting them across steps forces memory work. Rule of thumb: one-per-screen when the user *gives* one thing; combined-view when the user *reads* several things. [NN/g (working memory; questions-per-screen in forms research), Baymard (needless pagination), Few] [judgment]
31. **Infinite feeds and pagination are for unbounded archives; bounded meaningful sets (today's workout, this week) render whole.** Plain English: "load more" mechanics belong where content is endless and ranked by recency. A workout of 6 exercises or a week of 7 days is a bounded set with a shape — show all of it so the user sees the whole and their position in it. Chopping a bounded set into pages destroys the overview that is the set's whole point. [NN/g (list pagination guidance), Few (whole-picture dashboards), Baymard] [mechanical]
32. **Density on desktop widths comes from multi-column zoning, not from scaling up the phone column or cramming more rows.** Plain English: at desktop, the phone's single column becomes sparse. The right response is spatial: place zones side by side (the reference mock's three macro columns), widen data displays, show the comparison panels a phone had to hide behind taps. The wrong responses are stretching one column full-width (violates UX Canon 04 #26) or keeping the phone layout and calling the emptiness "clean." Same content, redistributed — not same layout, inflated. [M3 canonical layouts / window size classes, HIG (iPad/desktop multi-column), RUI, House north star (applies at all widths; reference mock has three aligned macro columns)] [judgment]
33. **When viewport height is short (landscape phones, split screen, keyboards up), the screen sheds in reverse priority order — decoration first, secondary data second, the task last.** Plain English: with a keyboard open, a 384×~300px window remains. Screens with inputs must define what disappears first: atmosphere/illustration goes, then supporting stats, and the input plus its confirm button remain reachable without scrolling. If nothing was designated sheddable, the keyboard decides for you at random. [HIG (keyboard avoidance), M3 (window size classes, compact height), VWIG] [mechanical]

## 6. Breathing Room as Hierarchy: Whitespace Must Be Unequal

34. **Whitespace is an active grouping instrument, not leftover background: every gap on the screen either binds (small), separates (large), or is a mistake.** Plain English: on a cardless surface there are no boxes to say "these belong together" — the gaps carry that entire message alone. So no gap is neutral: audit a screen by asking of each vertical space "what relationship is this asserting?" A gap with no answer is noise. This is the screen-level generalization of proximity (UX Canon 04 #23). [Gestalt proximity via NN/g, RUI, House north star (whitespace listed as an explicit replacement for cards)] [judgment]
35. **Unequal gaps ARE the structure: each spacing level must be ≥2× the level below it — zone over group, group over within-group. Equal spacing everywhere = zero structure.** Plain English: a screen where everything is 16px apart is a list of unrelated items — the eye gets no grouping signal and reads it as one undifferentiated column. The ratios must be *obvious at a glance*, not measurable-but-subtle: 8px inside groups / 24px between groups / 56px between zones (the 06 #8 table) reads instantly; 14/16/20 reads as sloppy equal. The ≥2× floor binds the values actually used on a screen: if within-group runs at 12, group gaps run at 24, not 16. When a screen feels "flat," the first check is whether its gaps are actually unequal. [RUI, Gestalt/NN/g, M3 spacing, UX Canon 04 #23; 06 #8] [mechanical] *(patched 2026-07-23: 1.5× low end raised to the ≥2× floor per 06 #8)*
36. **Macro whitespace obeys zone logic, micro whitespace obeys group logic — and they never trade: cutting macro space to fit more groups destroys the zone map.** Plain English: macro space (between semantic zones) is the screen's table of contents; micro space (within groups) is line spacing. Under viewport pressure the temptation is to shave the big zone gaps because they're the largest targets — but those gaps are what make the screen legible as regions. Compress *within* groups first (they have the compact tier's headroom), and drop content before collapsing zone boundaries below distinguishability. [RUI, Few, House north star (semantic zones perceived through composition)] [judgment]
37. **Whitespace substitutes for dividers, not accompanies them: where a gap already separates, adding a rule/border double-charges; where space is too tight to separate, a hairline is the cheap fallback.** Plain English: separation costs either pixels (a gap) or ink (a line) — paying both is the bordered-AND-padded look that reads heavy. On this product, prefer the gap (north star). Use the subtle divider precisely where the vertical budget can't afford a full separating gap (dense tables, compact rows) — the divider is the *dense-context discount substitute* for whitespace, never a decoration on top of it. [RUI (spacing → background → border, in that order; UX Canon 04 #66), Tufte, House north star (subtle divider lines listed as an allowed tool)] [mechanical]
38. **Emphasis by isolation: the most important element on an airy surface gets the most empty space around it — and isolation only works if it's scarce.** Plain English: surrounding one element with unusually generous space marks it as the point of the screen (the hero action, the milestone number). This is a spotlight, and a screen full of spotlights lights nothing: at most one isolation-emphasized element per screen. On dense surfaces, emphasis comes from scale/weight instead (UX Canon 04 #51), because there is no space to spend. [RUI, NN/g (visual salience), Few] [judgment]
39. **A density SHIFT is itself a signal — place dense and airy regions deliberately, because the boundary between them reads as meaning.** Plain English: when a tight data table sits below an airy hero, the texture change says "overview above, detail below" — that's composition working for free. But an accidental density change mid-zone (one group airy, its sibling tight) reads as two different apps glued together. Density must change AT zone boundaries and stay constant within them. The north star names "shifts in visual density" as an explicit card-replacement tool; this is the rule for wielding it. [House north star (density shifts as segmentation), RUI, UX Canon 04 #34 (one density per surface — refined here to: one density per zone, deliberate shifts between)] [judgment]
40. **Whitespace asymmetry binds labels to their content: space above a heading ≥ ~2× the space below it.** Plain English: a heading floating equidistant between the section it ends and the section it starts belongs to neither. The tight side of the gap points at what the heading owns. This one ratio, applied everywhere, is the difference between a screen that self-organizes and one that needs borders to explain itself. Screen-level restatement of proximity for the cardless case. [RUI, BPT-adjacent typography consensus, Gestalt/NN/g] [mechanical]
41. **Optical density beats mathematical density: equal token gaps around unequal elements look unequal — adjust by eye at zone boundaries.** Plain English: a 48px gap above a tall dark illustration and a 48px gap above a thin text line do not look like the same gap; large, dark, or full-bleed elements need more surrounding space to *appear* equally separated. Tokens set the baseline; the eye finalizes zone-boundary spacing (this is UX Canon 04 #32's optical-adjustment license, scoped to macro space). [RUI, HIG (optical alignment), UX Canon 04 #32] [judgment]

## 7. Measure and Text-Block Width at Screen Level

42. **Prose never spans the full content column on wide viewports: cap text blocks at ~65ch (band 45–75ch) even when the layout around them runs wider.** Plain English: the element-level measure rule (UX Canon 04 #5) has a screen-level consequence: on tablet/desktop, the layout grid may be 1200px wide but any paragraph inside it still gets its own ~600px max-width sub-column. Data displays, charts, and headings may run wide; sentences may not. A screen is allowed to have different widths for different content types — that's composition, not inconsistency. [BPT, RUI, NN/g, UX Canon 04 #5, #26] [mechanical]
43. **At phone width, the full content column IS a good measure — never sub-inset prose on phones to chase an ideal character count.** Plain English: 384px minus margins ≈ 350px ≈ 40–45 characters at body size — already at the band's edge. Adding side insets to phone prose "for readability" spends scarce width to make the measure *worse* (shorter). The phone answer to measure is: full content width, adequate line-height, nothing else. [BPT (measure math), RUI, §3 horizontal budget (#13)] [mechanical]
44. **Wide-viewport text placement: anchor prose to the layout's reading edge and let the remaining width go to margin or side-content — never center a lone text column in a void without a compositional reason.** Plain English: when a 65ch column sits in a wide screen, the leftover width must look intentional: either the column anchors left with the rest of the layout (continuing the screen's spine), or the space is used for context (secondary column, marginalia, atmosphere). A skinny centered column floating in blankness reads as an unstyled document — the desktop version of the dead-zone defect (#21). Centering is fine when the whole screen is a centered composition (onboarding, celebration). [RUI, NN/g, House north star (one coherent visual model at all widths)] [judgment]
45. **Multi-line text in dense rows is a density failure: in compact lists and tables, values fit one line (short labels, truncation per UX Canon 04 #20/#154, or a wider layout) — wrap-happy rows destroy the row rhythm that makes lists scannable.** Plain English: a compact list earns its density from uniform row heights; one row wrapping to two lines breaks the scan rhythm for the whole list. Design compact rows so their content cannot wrap at 320px (test with long exercise names), or promote the surface to a roomier layout that wraps everywhere uniformly. [Baymard (list scannability), NN/g, Carbon/Polaris (table cell behavior), UX Canon 04 #35] [mechanical]
46. **Headline size scales with available width, but headline WRAP count doesn't: display text at any width runs 1–3 lines max — if it wraps more, shrink the type or shorten the words.** Plain English: a 40px headline wrapping to five lines at 320px devours the viewport and reads as an error. Fluid type (clamp between floors and ceilings) plus copy discipline keeps the identity moment big *and* short at every width. [RUI, VWIG (fluid type), UX Canon 04 #155, House north star (editorial display type)] [mechanical]

## 8. Progressive Disclosure: The Density Valve

47. **When a screen exceeds its density budget, move content behind interaction rather than compressing everything to fit — hiding the secondary beats shrinking the primary.** Plain English: the two ways to resolve "too much for this screen" are compress (smaller, tighter — costs legibility of everything) and defer (a tap away — costs access to that one thing). Past the legibility floors (type floor, touch floor, gap tiers), defer is always the right valve: the primary content keeps its size and the secondary pays the tap. Compression that violates any floor to keep everything visible is never the answer. [NN/g (progressive disclosure), HIG, M3, UX Canon 04 #153 (element form of this rule)] [judgment]
48. **What goes behind the tap is decided by frequency-of-need, never by importance-to-the-business or by what fits: the thing needed on most visits stays visible; the thing needed on few visits defers.** Plain English: measure (or honestly estimate) how often each element is actually used at that moment. Mid-set: weight/reps visible; exercise-technique video deferred. History row: date + headline stat visible; per-set breakdown deferred. Getting this backwards — burying the frequent thing because the rare thing was prettier — is the canonical disclosure failure. [NN/g (progressive disclosure: frequency and predictability decide the split), Few] [judgment]
49. **Disclosed content must be predictable from its trigger: the visible part is a truthful summary of the hidden part (count, headline value, or delta), never a bare chevron.** Plain English: the user decides whether to tap based only on what the collapsed state shows — so the collapsed state must carry the scent: "5 sets · top set 225×5 ▸" lets the user skip the tap when the summary suffices, which is the whole efficiency win. A row that says only "Details ▸" forces exploratory taps, which users stop making. [NN/g (information scent; predictability requirement of disclosure), Baymard (truncated content labels)] [mechanical]
50. **One level of disclosure on phones: tap reveals answer, not another menu of taps.** Plain English: disclosure behind disclosure (tap → sheet → "see more" → screen) makes content effectively unfindable and is the sign that the top-level screen's information architecture is wrong, not that another layer is needed. If content seems to need two layers of hiding, it belongs on its own screen reachable by navigation instead. [NN/g (disclosure depth), HIG (navigation vs. disclosure)] [mechanical]
51. **Focus+context over navigate-away for mid-task detail: expand in place (accordion, inline reveal, sheet over context) when the user must return to where they were; navigate to a new screen when the detail is a destination.** Plain English: mid-workout, opening exercise detail must not lose the user's place in the workout — reveal within or over the current surface so context stays visible and return is one dismissal. NN/g's mobile-accordion endorsement applies: on phones, in-place expansion beats page-jumping for subordinate content. Full navigation is for content the user seeks as a destination (history, settings). The north star names focus+context as the product's interaction model; this is its density application. [NN/g (accordions on mobile; preserving context), HIG (sheets/modality), House north star (focus+context interaction)] [judgment]
52. **Never disclose the safety-critical or the legally-required: content the user must see (injury warnings, destructive-action consequences, costs) cannot live behind an optional tap, whatever it does to the density budget.** Plain English: progressive disclosure is for content the user may *choose* to skip. Anything where skipping causes harm (a form-critical safety cue mid-exercise, "this deletes your history") is exempt from the valve — it stays visible and the screen makes room by deferring something optional instead. [NN/g, HIG, WCAG (timing/visibility of essential information), UX Canon 04 #135] [mechanical]
53. **Hover-only disclosure is forbidden as the sole access path — every deferred item is reachable by tap/focus, because the primary device has no hover.** Plain English: on a phone-first product, tooltips and hover-reveals are enhancement for pointer devices only; any content that exists *only* on hover is invisible to the entire phone audience. [NN/g, WCAG 1.4.13, VWIG, UX Canon 04 #98 (charts form)] [mechanical]
54. **Disclosure state defaults follow the screen's mode: working surfaces open with today's relevant section expanded and the rest collapsed; reading surfaces open with everything visible unless length is unmanageable.** Plain English: a workout screen auto-expands the current exercise and collapses completed ones (the mode knows what matters now). A plan-review screen shows the whole plan — collapsing it into ten closed accordions forces ten taps to read what one scroll would give. Collapse-by-default is a working-mode tool, not a tidiness tool. [NN/g (accordion default-state research: don't force serial opening for content meant to be read through), Few] [judgment]

## Contested / no-consensus

- **"White space always improves comprehension" vs. expert-user density preference**: NN/g-cited academic work (Lin 2004 and successors) shows whitespace improving comprehension and satisfaction for reading tasks; enterprise research and practitioner consensus (Carbon, Fluent, Bloomberg-terminal lineage, RUI's own dense-UI passages) show expert daily users preferring and outperforming with high density. Both are right in their contexts — which is why every rule above is conditional on screen mode — but the field has no unified equation. **The boundary case for THIS product is resolved by owner ruling (2026-07-23, decision log): lean dense on logging surfaces, airy elsewhere — with the owner's explicit caveat that density must not be overdone; when it starts to feel like too much, lean back toward white space.** [contested in the field — house-resolved]
- **The fold in 2026**: NN/g maintains the fold matters (attention concentrates in the first viewport); a sizable practitioner camp holds that mobile-native users scroll so readily the fold is dead as a constraint. Data supports both: users scroll easily AND weight the first viewport heavily. This file takes the NN/g-compatible middle (#26–#28: primary content above, scent below), but the pure positions are genuinely irreconcilable. [contested]
- **User-selectable density toggles** (comfortable/compact controls, as Gmail/Carbon/Fluent tables offer): enterprise systems formalize them; consumer-app consensus (HIG, most mobile products) is that density is the designer's decision and toggles are complexity users shouldn't carry. For a phone-first consumer fitness app the no-toggle position is assumed above, but it is a camp, not a law. [contested]
- **One-question-per-screen onboarding**: conversion-optimization practice (Typeform-style, most fitness-app onboarding) swears by it; forms researchers (Baymard, some NN/g findings) document that needless pagination inflates abandonment and that grouped short steps can beat atomized ones. #30 splits the difference by capture-vs-read, but the onboarding-specific evidence genuinely conflicts. [contested]
- **Accordions and tabs as mobile density valves**: NN/g endorses mobile accordions; SEO/content practitioners and some usability work warn hidden content is unread content (and historically down-weighted by crawlers). For in-app surfaces the SEO half is irrelevant, but "collapsed = effectively deleted for most users" has real supporting data and argues for less disclosure than #47 permits. [contested at the margins]
- **Density decrement mechanics**: M3 formalizes density as component-height decrements (−4dp steps) while keeping 48dp touch targets via invisible padding; HIG has no density system at all and simply prescribes generous fixed metrics; Carbon/Fluent/Polaris each ship their own compact variants with different floors. There is no cross-system standard for HOW MUCH a compact mode compresses — the tiers in #20/#22 are a synthesis, not an industry number. [contested]
- **Glance-time numbers**: the ~2-second glance budget (#8) comes from automotive safety research (NHTSA driver-distraction guidelines) and wearable design practice, not from controlled gym-context studies; mid-workout attention is plausibly similar (divided attention, motion, urgency) but the transfer is an analogy, not a finding. [no direct evidence]
- **Exact ratio thresholds**: the ≥2× zone-gap and ~2:1 heading-space ratios (#35, #40) are practitioner consensus (RUI and design-system convention), directionally supported by Gestalt research but never validated at those specific numbers. The *inequality* requirement is solid; the multipliers are craft convention. [contested at the margins]
